Email Agent — a field guide

The machine that must not act

A local AI tool that reads your Gmail, decides what is junk, and then goes to considerable lengths to avoid touching anything. This is why.

Written against feature/todos-w11-bugfixes, 129 commits ahead of main — the unlock gate of § 08 and the verification pass of § 07 have not landed on main yet · 838 Node tests and 45 component tests, all passing · every claim checked against source · fifteen merged pull requests plus a five-milestone wave of context

§ 01

Would you let a language model into your inbox?

Most people say yes with a caveat: sure, as long as it asks me first. A dialog appears, you read it, you click Approve, the change happens. That instinct is right, and it is also the entire problem, because of one detail that sounds pedantic until it destroys your mail.

“I click Approve” and “Gmail changes” are not the same instant. Between them sits a database write, a process boundary, and a network call to Google that can take a second or hang for fifteen minutes. Everything peculiar about this codebase — a queue, a claim token, a hand-written parser for TypeScript, a five-line comment about a database returning ten rows — lives inside that interval.

Gmail APIGoogle’s HTTP interface to a mailbox. Moving a message to Trash is a request that either succeeds or does not; there is no transaction spanning it and your local database.

So read this page with one reframing in mind. This is not an AI email tool with a safety feature bolted on. It is an apparatus for not trusting the model, and the AI is a component inside it.

One message is carried the whole way through, so that nothing here is abstract: m18f3, subject “Your weekly deals from Nordpost”, unread, from news@nordpost.example. It gets fetched, embedded, read by an action, proposed for archiving, queued, approved, applied. When a section is about failure, it is m18f3 that fails.

§ 02

One machine, one user, no server

Everything runs on your laptop. There is no backend, no user account, no multi-tenancy. The “web UI” is a Next.js app bound to 127.0.0.1 that only your machine can reach; the database is a directory under ~/.email-agent; your Gmail credentials sit in a file next to it. There is now a browser session — you unlock the UI once with a printed one-time link — but that is a lock on a door, not an identity. Nobody signs in as anybody. § 08 is entirely about why that lock exists and exactly how little it buys.

loopbackThe 127.0.0.1 address, which only the local machine can connect to. Binding here is a real boundary: an off-box process cannot open the socket at all, whatever headers it would have sent.

Every credential file under ~/.email-agent/ — the OAuth tokens, the settings, the session store — is written mode 0600, and the directory holding them is 0700. All three were 0644 inside 0755 until August 2026 — measured, not assumed: neither the settings writer nor the token writer passed a mode, and the default umask is 022. Among the world-readable files was the Gmail refresh token, which needs no password and stays valid until somebody revokes it.

The database was the exception, and this page’s own fact-check is what found it

Fact-checking this page against the instruction file’s old “everything under ~/.email-agent/ is 0600 inside 0700” turned up a real gap, not a documentation nit: the mail itself is written by LanceDB into a directory that was created with no mode at all, so data/lancedb landed 0755 — and on a fresh install, where nothing had yet written settings, the app’s own root directory landed 0755 too, leaving no shield anywhere in the chain. That is fixed now: every directory this app creates, root to leaf, is forced back to 0700 on every write, which also repairs a tree an older version left loose. What is still true, and always will be, is narrower: LanceDB creates the *.lance table directories and their manifests itself, at its own modes — 0755 and 0644 — and nothing here touches those. What protects the mail inside them is the 0700 on every directory above, not a mode on the mail files themselves; POSIX requires execute permission on each directory in a path to traverse it, so an unreadable ancestor makes the readable leaf unreachable. Those are different guarantees, and the instruction file now says so instead of overstating the first one.

The code is a monorepo of three packages, and the split matters because it is also a trust split.

PackageOwnsNotably does not own
@email-agent/core Gmail access, the database, the AI executors, the action system, the approval queue Any user interface
@email-agent/web The Next.js UI and its API routes — mail list, actions page, approvals panel, settings. Reachable only after a browser has completed the unlock exchange. Direct Gmail writes; it goes through core’s queue like everything else
@email-agent/cli The email-agent command — setup, fetch, run-action, approvals, unlock, serve Deep imports into core; it may only use the public barrel

One recent wrinkle is worth naming because it is the sort of thing an architecture diagram hides: serve used to be a thin wrapper that spawned the Next.js server and got out of the way, with no dependency on core at all. It now opens the database first, to run a check described in § 07. Starting the web UI is no longer free.

§ 03

Why there is no password field

The app never sees your Google password, and could not use it if you gave it one. Instead Google hands out two different pieces of paper.

OAuth2A protocol for granting an app narrow, revocable access to your account without sharing your password. You approve once, on Google’s own site.

An access token is a short-lived pass — roughly an hour — that proves the app may act on your mailbox right now. A refresh token is the long-lived stub that lets the app mint fresh access tokens without asking you again. Both live in ~/.email-agent/accounts/{email}/token.json, now at mode 0600.

Two properties follow, and they are the whole reason for the complexity. The grant is scoped: this app asks for Gmail modification and nothing else, so the same credential cannot read your Drive. And it is revocable independently: you can kill this app’s access from Google’s security page without changing your password or disturbing anything else you have signed in to.

Which mailbox, exactly?

The tool supports several Gmail accounts, so every operation has to answer a question that turns out to be safety-critical: whose mailbox is this? Getting it wrong does not throw an error — it archives the right message in the wrong account.

ADCApplication Default Credentials — whatever identity the gcloud command-line tool is currently signed in as. Convenient for developers, ambient, and easy to change without noticing.
The refusal is the feature

If you name an account and its stored credentials are missing or broken, the client throws. It does not quietly fall back to whatever gcloud happens to be signed in as. A fallback here would send writes to a different mailbox than the one you asked for, and every message id would still resolve, because ids are per-mailbox.

The empty string "" is a deliberate sentinel meaning unscoped — use ambient credentials. It is a legitimate mode, and it carries a documented cost that has grown rather than shrunk: a row queued under "" is resolved against ambient identity at three separate moments now — when it is queued, when it is approved, and when the verification pass in § 07 reads it back. ADC can have moved between any two of them.

On the apply path that is survivable, and for a reason worth being precise about: Gmail message ids are per-mailbox, so a call aimed at the wrong account simply 404s and the row resolves failed. That is a property of Gmail’s id space, not a guard this code implements, and the difference matters — on the read-back path it does not hold, which is why the verifier is forbidden from ever recording an "" row as applied.

§ 04

Turning an email into 768 numbers

Fetched mail lands in LanceDB, an embedded vector database — a library that reads and writes files in a directory, not a server you connect to. Alongside the subject and sender, each row stores an embedding.

embeddingA list of numbers — here 768 of them — produced by a model from a piece of text, arranged so that texts with similar meaning land near each other in that 768-dimensional space.
Naive design

Search the mail by keyword. Find every message containing “unsubscribe”.

Where it breaks

A newsletter that says “manage your preferences” is invisible. Keywords match spelling, and the thing you actually want to match is meaning.

The embedding solves that by making meaning geometric: two emails that a person would call similar end up close together, whatever words they used. Distance becomes a proxy for similarity.

And now the honest beat, which is more interesting than the capability. This repo builds that vector space and never searches it. There is no nearest-neighbour query anywhere in the product — not one call to LanceDB’s vector search API. The only code that walks the space at all is the clusterer, which runs k-means over the stored vectors using plain Euclidean distance. A capability that is built is not a capability that is used, and it is worth saying so out loud rather than letting “vector database” imply the rest.

Five things this database is not

Each of these contradicts a reasonable assumption, each was established by running the database rather than reading about it, and each cost something real.

MVCCMulti-version concurrency control. Writers do not lock; each commit produces a new version, and a conflicting writer is refused rather than silently interleaved.
You would assumeWhat was measuredWhat it cost
A query returns all matching rows. Any query without an explicit limit returns 10 rows. Not just vector searches — all of them. limit(0) is not “no limit”; it is zero rows. 15 of every 25 queued changes were invisible on every screen. Worse, a safety read-back was capped at 10 while batches were exactly 10, so an apply could mutate Gmail for rows it never learned it owned.
Filters combine. Calling the filter method twice replaces the first condition instead of adding to it, silently. where(A).where(B) matches B alone. Every filter now has to be assembled into one string by hand. The two filter builders return arrays for exactly that reason — so a caller has something to join with AND and cannot chain by accident.
A table handle stays current. A handle is pinned to the version it was opened at. Stale reads return old rows silently; stale writes throw. The retention sweep quietly stopped running whenever anything else was writing.
Column names are case-sensitive. The SQL parser lowercases unquoted identifiers, so accountId becomes accountid and does not exist. Every camelCase column has to be written in backticks, forever.
It cannot add a column to an existing table. It can. addColumns adds in place, preserving every row. The belief that it could not caused ~950 lines of crash-recovery machinery to be written, reviewed adversarially twice, then deleted.

There is one more that has no defensive workaround, only awareness: there are no parameterised queries. Every filter is assembled as text, so every value that reaches one has to be escaped by hand.

Every one of those five is a fact about one version of one library. They are written down that way on purpose, with the version number attached, because the next upgrade invalidates all of them at once.

§ 05

Two shapes wearing one interface

An action is a prompt plus a name. Running one means sending your mail and that prompt to a language model. The tool can reach a model in two fundamentally different ways, and the difference is not cosmetic.

It can spawn a command-line tool as a subprocess — the claude, codex or gemini CLI you already have installed. Or it can make an HTTP request to a provider API with your key. A strategy interface hides which, and a router picks by availability.

“Available” had to be tightened, and the reason is a good illustration of the difference between the two shapes. The gemini check originally asked is the binary installed? With the CLI present and never signed in, that answered yes, the router chose it, and the CLI blocked on an interactive browser consent screen until a 120-second timeout — one dead run per attempt, reported as a timeout. The question a subprocess executor has to answer is can this run a prompt?, so it now also requires credential material to exist and spawns with browser-opening disabled, failing in about two seconds with a message that names the fix. Neither check proves the credentials work. Only a real call can, and no successful gemini run has ever been observed from this project.

The word “token” means five different things here

This is worth pausing on, because the collision is genuinely confusing and the codebase hits all five within a few files of each other. It was three when this page was first drafted; the browser unlock work added two more, which is its own small lesson about vocabulary.

Which tokenMeans
OAuth tokenA credential from Google — access or refresh. § 03.
LLM tokenA chunk of text, roughly ¾ of a word, that a model bills and limits by. This section.
claim tokenA fresh identifier stamped on queue rows so one apply can prove which rows it owns. § 07 — and it is the load-bearing one.
unlock tokenA one-time, ten-minute secret printed on your terminal that opens the web UI in a browser. § 08.
session & binding tokensThe pair the unlock exchange returns: one in a cookie, one in origin-scoped browser storage. Counted as one sense because they are two halves of one credential. § 08.

The LLM sense produced a real defect. There is one integer column recording tokens used, and five executors were each writing a different measurement into it. The Claude CLI executor recorded output tokens alone. Codex summed a cached-input field that was already inside the input count, double-billing itself. Gemini read a total-count field its CLI does not emit, and so recorded 0 forever.

Measured — a live one-word reply from the Claude CLI

input 2 · cache_creation 13901 · cache_read 15242 · output 4. The executor recorded 4. The real total is 29,149.

The root cause is that providers disagree about whether cached input is included in or additional to the input count. Anthropic’s cache fields are additive; codex’s cached field is a subset. So one module now owns a single definition — all input at full weight plus all output; a measure of work, not of money; 0 means “not reported”, never “free” — with one normaliser per provider family. Rows written before that change are not comparable with rows written after, and nothing in a row says which side of the line it is on except its timestamp.

§ 06

An LLM writes code that runs as you

You can ask the chat UI for a new action in English — “flag anything from my landlord” — and a model writes it. Follow what that actually means:

  • You describe the action in the browser.
  • A model writes a TypeScript file.
  • The file is saved to ~/.email-agent/actions/.
  • Later, the app loads it.
ESMThe JavaScript module system. Its import does not just read a file — it evaluates it. Any code at the top level of the file runs immediately.
Naive design

To load the action, import() the file and read its exported object.

Where it breaks

Importing is executing. The moment that file is imported, anything at its top level runs — with your permissions, in the same process that holds your Gmail tokens. And the file was written by a language model.

The first defence was a denylist: scan the source for dangerous names before loading it. It was defeated in one line.

The real fix went further than checking the file before importing it. The file is never imported at all. It is parsed, and the action object is computed directly from the syntax tree — so the code never enters the module system and never has an opportunity to run.

ASTAbstract syntax tree — a program represented as structured data rather than text. Analysing this is precise where scanning text is guesswork.

One subtlety is worth carrying away, because it is the sharpest idea in the codebase. An earlier version of the allowlist accepted this line:

declare const process = "safe"

It looks like it binds a harmless string to the name process. It does not. declare is a TypeScript ambient declaration — it asserts that something exists elsewhere and is erased entirely at runtime, so every later mention of process reaches the real, global one. The guard had recorded the name as safe data.

The lesson

When judging whether a piece of syntax is safe, the question is not “does this look inert?” but “does this bind what it appears to bind at run time?” The same question refuses using (whose disposal hook is a call the file never spells) and __proto__ as an object key (which sets a prototype rather than binding a property).

Not executing the file is only half the contract. The value the parser hands back has to be the value Node would have produced, or the evaluator is describing a different module than the one on disk. So a named export is read as a live binding at the end of the walk, while a default export snapshots its operand where it stands; and a file the runtime would reject outright is refused rather than evaluated, because the parser’s syntax pass does not catch the errors a strict-mode module would raise. Where the semantics cannot be matched, the rule is to refuse, never to guess.

One code path does all of this. The save-time guard, the loader, and the reader that extracts an action’s id are literally the same traversal — the guard is the extractor with the values thrown away. The web package kept its own regular expression for reading an id until recently, and deleting it was not a tidy-up: a second implementation of a safety rule drifts, and the drift is the bypass.

§ 07

Never do the thing. Write down that you would like to.

Here is the heart of it. Our message — m18f3, “Your weekly deals from Nordpost” — has been fetched, embedded, stored, and read by the junk action, which has decided it should be archived. What happens next is the product.

Naive design 1

Apply the change, then show the user a report of what was done.

Where it breaks

The user never got to say no. A model that is wrong two percent of the time, over a batch of four hundred, is eight mailbox changes a run that nobody consented to.

Naive design 2 — the one most people would ship

Write the proposals to a table. Show them. When the user clicks Approve, read the pending rows and call Gmail for each one.

Where it breaks — and this is the important one

There are two surfaces. Suppose you hit Apply in the browser, and while those Gmail calls are in flight you change your mind and run email-agent approvals reject in a terminal. The reject looks at the table, sees rows still marked pending, marks them rejected, and tells you: “3 changes rejected.” Then the apply finishes and writes applied over the top.

Your mail was destroyed after you personally refused it, and the record says you approved. That is the exact failure this whole feature exists to prevent, reproduced by the feature itself.

claim tokenA freshly generated identifier stamped onto rows at the moment they are taken, so a worker can prove which rows are its. The third of the five unrelated meanings of “token” on this page.

Move 3: claim the rows before you touch Gmail

A row does not go straight from pending to applied. It passes through applying, and it gets there by a single atomic update whose condition requires that the row is still pending. That update stamps a freshly minted claim token onto whatever it moved. The caller then reads back by that token — and that is how it learns which rows it actually won.

Now the race resolves correctly. The reject arrives, looks for pending rows, finds none, and says so honestly.

This is also why both surfaces distinguish “this run claimed nothing” from a no-op. When the web UI reports rows as skipped, or the CLI calls them unclaimed, the number means exactly one thing: this call did not claim these rows. Not “already applied”, not “already rejected” — the row might be mid-apply in a request that is still running, might have failed earlier, or might not exist. Both messages offer those as possibilities and assert nothing further.

The states, named by what they mean to you

Five states, and the interesting thing about them is which edges exist. A row can be approved, rejected, or applied. It can also end up applying with nobody left to finish it — the state a crash invents. Leaving that state takes evidence, and the queue records which kind of evidence it was.

Chunks of ten, and the bound that is easy to overstate

Applies happen in chunks of ten, and each chunk claims its own rows immediately before calling Gmail — the claim sits inside the loop, not before it. That is deliberate: it makes the claimed set and the in-flight set coincide, so a crash strands at most one chunk, and every later row is still pending and still yours to approve or reject.

The bound is per call, not per batch

Say it that way. At most one chunk of this invocation can be stranded, and every id this invocation had not yet reached is still pending. Two concurrent applies leapfrog — A claims 1–10 and starts calling; B loses those, continues, and claims 11–20 while A is still in flight — so one crash with two callers strands two chunks. Nothing serialises applies at batch level, and the documentation says so rather than restating the per-call bound as a per-batch one.

The applies themselves are serial: one Gmail round trip at a time, one outcome per operation, paired positionally with the rows that were claimed. Gmail offers a batch-modify call, and it is deliberately not used — its success response body is empty, so it reports no per-message result, and N rows would collapse onto one all-or-nothing status. That is exactly the ambiguity this design fails closed on.

Move 4: the state the claim protocol invented

A row left in applying is in a genuinely strange position. It is not pending, so it cannot be approved or rejected — the claim protocol makes sure of that, which is exactly right, because re-applying might be the second trash of an already-trashed message. But it is also invisible to every screen, because every screen lists pending.

So the mechanism that fixed naive design 2 created a failure mode of its own, and that failure mode needed its own answer. There is a separate report of rows claimed for more than fifteen minutes, and the question is what to do with it.

Naive answer 1

Retry the chunk.

Where it breaks

The request may have reached Google and been recorded before the crash. A retry is a guess dressed as a fix.

Naive answer 2 — and this one shipped

Show the user the rows and ask. Two buttons, no retry, and the confirmation says plainly that the app cannot check for you.

Where it breaks — quietly

The user is being asked a question the app could have answered itself, about a mailbox they now have to go and inspect by hand, one message at a time. Honesty is not the same as helpfulness.

Move 4, continued: check Gmail, then ask about what is left

The verification pass reads each stale row’s current labels from Gmail and compares them against what the operation was trying to achieve. This is possible for a reason that is a property of the operation set rather than a clever trick: every mutation this app performs is idempotent label state. Archive removes INBOX. Trash adds TRASH. Spam adds SPAM and removes INBOX. There is no send, no counter, no permanent delete anywhere in the write module. So “did this land?” has an observable answer.

Two of the predicates are worth printing, because both were got wrong once:

  • spam needs SPAM present and INBOX absent. The spam operation is one atomic modify carrying both, so that pair is the intended end state. A draft predicate table said “SPAM present” alone, and was wrong.
  • trash needs TRASH present alone. Gmail drops INBOX implicitly when a message is trashed, so requiring its absence as well would manufacture false negatives.

And the beat that makes the whole thing feel designed rather than added: the pass reads the database first, and the database read is the gate. Zero stale rows means zero Gmail calls, zero printed output, and no clock read at all. That is what lets this run unprompted on every fetch, at every serve start, inline in approvals stranded, and once per mount of the web panel — without a daemon, without a poll, and without a notifications subsystem coming back from the dead.

The six reasons the machine hands a row to a person

It fails closed to the human path, never to a verdict. A residual row carries which reason it hit, because a person told only “we could not check” cannot act on it.

ReasonWhat it meansWill it resolve itself?
message-missing A 404 — and it is three-way ambiguous: permanently deleted, or an ambient-credential row now pointing at a different mailbox, or a trash/spam that worked and was later purged. So a 404 can mean applied, and is never auto-anything. No
credentials Gmail refused the credential. Google returns 403 for both permission and rate-limiting, in the same status code, so these cannot be told apart from the status alone. Maybe
check-failed The check itself failed, not the change — including a timeout. Maybe, on a later pass
unverifiable-operation A label row with an empty label list — which the apply path throws on, so this app could never have applied it — or an operation type the checker does not recognise. Never. Only a person closes it
unscoped-account A row carrying the ambient-credential sentinel. It may be read, and it may be requeued; it may never be recorded applied on that evidence. No
not-checked The whole-pass deadline ran out before this row. Nothing went wrong and nothing was looked at — it must not read as a failure. Yes, next pass
Why an ambient-credential row can be read but never credited

On the apply path, a row pointed at the wrong mailbox 404s harmlessly, because Gmail message ids are per-mailbox. The read-back is not symmetric. A wrong-mailbox 404 costs nothing — it becomes a residual. But a wrong-mailbox message that happened to carry the same id and already-matching labels would return a positive verdict. So such a row may be requeued for approval, which costs nothing, and may never be recorded applied, which would be a lie in the audit trail. One function owns that refusal, and every route to an “applied” write goes through it — because a duplicated check is exactly how the second route would silently lose it.

Three numbers, in order, and why they exist

Until August 2026 nothing under the Gmail message read supplied a timeout. A peer that accepted the connection and never answered — a captive portal, a half-up VPN — stalled the serial loop indefinitely, and with it fetch, serve (which runs this pass before spawning the web server at all) and the API route.

Measured — and the try/catch was no defence

A surrounding try/catch catches throws, not hangs. Without a timeout, a call against a server that accepts and never responds was still pending at four seconds and would have stayed there. The read type had declared a “timeout” error kind since the day it was written, and nothing in the system could produce one.

Three bounds now sit in strict order: 8 seconds for one HTTP request, 10 seconds for the whole read, 20 seconds for the whole pass. The honest ceiling is 30 seconds, not 20, because the budget is checked before each read and the read that starts just inside it runs to its own bound. Quoting 20 as the ceiling would be wrong by a third.

The timeout option itself is a fact about one library version. It is declared in the HTTP client’s types and never read by that client’s own code — it works only because the installed version hands its options verbatim to an underlying fetch implementation that does honour it. A major upgrade would keep the option compiling and silently remove the bound.

Three limits, printed as limits

Do not describe either path — the machine’s or the person’s — as recovery. Both record an end state or hand the row to a person. Nothing is re-applied and nothing is rolled back. Three limits survive the design and cannot be engineered away.

Limit 1 — attribution, and it is benign

The check reads the state now and cannot prove this app’s call caused it. No check, automated or human, distinguishes “we did this” from “it was already like that”. A message you archived by hand five minutes earlier is credited to the app: end state right, authorship wrong. This direction is harmless — the row simply retires.

Limit 2 — the mirror, and this is the dangerous direction

An apply that really landed and was then undone by you — un-archived, re-marked unread, restored from Trash — verifies as not applied and is re-proposed as an ordinary pending row needing an explicit approval. Approving it again can undo your own later action. The honest sentence is this one: idempotent, therefore it cannot destroy anything; it can still undo something you did in between.

Limit 3 — narrowed, never closed

A hung apply landing between this pass’s read and its write can falsify a “not applied” verdict — and only that verdict; labels the check saw present were present, so a late apply agrees with an “applied” record. So every requeue candidate, and only those, is re-read immediately before adjudication, collapsing the exposure from a whole serial read pass plus two batch writes down to one read and one write. Re-reading the applied set would buy nothing and spend quota. The remainder is irreducible: Gmail can still land between that re-read and the write, because an external system and a local database cannot be read and written atomically. Write “narrowed”, never “closed”.

Two details of limit 3 are worth having. A re-read that fails never falls back to the first read — no verdict on evidence that could not be refreshed, so the row stays put for a person. And none of this could be fixed by claiming before reading: a crash between claim and release would re-stamp the claim time and hide the row for another fifteen minutes, which is strictly worse than the problem.

A record of who said so is not a proof

Two columns on the queue carry that theme, and both are worth understanding as documentation rather than as mechanism.

approvedVia records which surface claimed a row — web, CLI, auto-apply, or a sentinel for unclaimed-or-legacy. It is written by the single function through which a row leaves pending, as a required parameter with no default. It is attribution only: it gates nothing and proves nothing, and must never be read as a security control, because there is no unforgeable in-process caller identity to derive it from. It is exactly as trustworthy as the caller that set it.

resolutionEvidence records how a stranded row’s resolution was established — verified-api or user-confirmed. Both sources go through one write path, not two functions, and the note stamped on the row differs accordingly: the automatic one says plainly that it is an end-state match, not proof of causation. Its empty sentinel deliberately means three things at once — unresolved, resolved by its own healthy apply, or written before the column existed — and must never be rendered as “verified”.

The discipline in this corner

  • The age test lives inside the atomic update predicate, not as a check in JavaScript beforehand. A pre-filter leaves a window between reading the age and overwriting the claim token, and that stamp is destructive. The screens filter their lists by age; the ids they submit are just ids.
  • The count of rows changed comes from a read taken after the write. It can undercount and never overcount, and the reason is written down: undercounting understates what we did; overcounting claims credit for someone else’s decision.
  • The “it didn’t happen” answer puts the row back to pending, an ordinary proposal again, with the claim timestamp cleared so a future staleness check ages it from its next claim.
  • Every surface gives a shortfall’s cause as one of four possibilities, not three: an apply finished it; another person already answered it; Email Agent’s own automatic verification may have answered it in the meantime; or it was requeued, re-claimed, and is too new to adjudicate. The third is offered separately from the second on purpose — a user who pressed nothing themselves cannot guess that an automatic check exists.
The residual, stated rather than hidden

An apply that claims a row, calls Gmail, hangs past the fifteen-minute threshold, and then succeeds will lose its outcome — its write-back is scoped to a token the adjudication has overwritten, so it matches nothing. What you would observe: the change really is in Gmail, the queue row is pending again and re-approvable, and the audit trail says it never happened. The code detects this and logs it by row id; nothing prevents it. That adjudication can now come from the automatic verifier as well as from you. The alternative — letting the hung apply win — would leave a resolution unable to close out a row it has genuinely checked, which is the failure this surface exists to remove. The losing direction is chosen deliberately.

Say what remains, not the half that is covered. Verification narrows which rows reach that window — only the ones neither the API check nor a person has closed. It does not close the window.

The escape hatch, and its two locks

You can turn all of this off. One setting applies each batch the moment an action finishes. It is guarded by a second, separate setting — a recorded acknowledgement that you read the warnings — and the normalisation is one line:

autoApplyActions: autoApplyAcknowledged && gmail?.autoApplyActions === true

That runs on every read, in core and again at the web API boundary, so no path can arm unattended Gmail writes without the acknowledgement sitting alongside them. The CLI’s config set refuses both keys outright, with the reason recorded: that command cannot show you the warnings, so it must not record consent you never gave. The Settings page is the only surface that shows the cautions — and the honest framing in the code is that the invariant is consent-recorded, not UI-only: hand-editing both booleans into the settings file is still honoured.

Note what does not change: the queue is still written first, so the audit trail is identical. Turning this on changes when changes are applied, not whether they are written down. And one manual path stays immediate — per-email actions you click yourself in the mail UI apply straight away, because the click is the approval.

§ 08

How the browser is kept out

Because the web UI is a real HTTP server on your machine, two browser-level attacks apply. CSRF — cross-site request forgery — is a hostile page making your browser send a request to localhost:3847, riding your session. DNS rebinding is a page on evil.com re-pointing its own hostname at 127.0.0.1 so its requests are technically same-origin. The guards check the Host header against a local allowlist (which is what stops rebinding, since the browser still sends Host: evil.com) and require an Origin or Sec-Fetch-Site header that browsers always attach cross-origin.

The comment above them is refreshingly blunt about what that is worth: every one of those inputs is a header, and a non-browser client controls all of them. “This is a speed bump, not the boundary.” The boundary is that email-agent serve binds the loopback interface — 127.0.0.1, reachable only from this machine — so an off-box process cannot open the socket at all.

One more measured trap in the same code

The Host header has to be read straight off the request. An earlier version derived it from the request URL, and Next composes that URL from the server’s own configured hostname — so every request arrived claiming localhost whatever Host was actually sent. It broke in both directions at once: the browser that opened the 127.0.0.1 URL the server itself prints got 403 on every mutation, and a DNS-rebound Host: evil.example was never seen at all, so the anti-rebinding property did not exist.

The hole the headers leave

Until August 2026 there was no secret at all. Anything that could reach the port and set two headers had the whole UI: your mail, your settings, your approval queue. The read routes were as open as the write routes, so a mutation-only requirement would have left confidentiality exactly where it was.

What shipped is a one-time unlock token. email-agent serve mints one and prints a link before spawning the web server; email-agent unlock prints a fresh one on demand, against a server that is already running — which is precisely why the token lives in a file rather than an environment variable, since no process can inject an environment variable into a running child. Ten-minute lifetime, burns on first use, and only sha256 digests are ever persisted.

Why the token is after a #, and why that is a defect fixed

The printed link is http://<host>:<port>/unlock?exchange=1#token=…. The part after the # is a URL fragment, and no browser ever sends it to a server: not to this one, not to a proxy, not in a Referer.

That is not a flourish. While the token rode in the query string, serve spawned a dev server whose request logger printed the complete request URL — so every unlock echoed the live token back into the same terminal a second time, while the code’s own comment claimed the plaintext existed on its stdout and nowhere else.

And state what it does not fix, without letting the claim grow. The token still reaches the browser. After the page clears the fragment it remains in the terminal scrollback that printed it, in the clipboard if it was copied, and possibly in the browser’s own history database — a navigation commits, fragment included, before any script runs. What the fragment removes is the copy that reached a server.

The sharpest fact on this page: cookies do not know about ports

The exchange could have ended with a session cookie and stopped there. It does not, because of a property of HTTP that no cookie attribute can repair.

Cookies are scoped by host and path, and never by TCP port

RFC 6265 §8.5 says so outright. 127.0.0.1:3847 and 127.0.0.1:9999 share one cookie jar. Another local process binds a sibling port, a cross-site top-level GET carries the Lax cookie to it, and that server is now holding a replayable bearer credential. httpOnly is no defence at all here — it stops page script from reading the value, and the party holding it is an HTTP server. The __Host- prefix needs Secure, which plain HTTP on loopback cannot set, and would not add port scoping even if it could.

What closes it is that web storage is scoped by origin, and an origin includes the port. So the exchange mints a second 256-bit value beside the session token, returns it in the response body — never as a cookie, which would hand it straight to the attacker — and the browser writes it into localStorage on the origin it actually opened. Every API call echoes it in a custom header, and the guard requires both halves.

A consequence follows that is worth stating because it looks like a weakness and is not. The page gate stays cookie-only and cannot do otherwise: a top-level navigation carries no custom header, so requiring the second factor there would mean nobody could ever load the app. That split is safe for a property of this app rather than a general one — every page behind the gate is a client component with zero server-side data fetching, so the most a cookie-only pass yields is the static app shell. The API guard is the enforcement; the page gate is UX. If a page ever fetches on the server, that page is a hole.

Scope it honestly, and do not let the claim grow

The gate closes exactly one hole: a bearer cookie replayed from a different loopback port. The cookie jar is still shared with every other port; what changed is that the leaked value is no longer sufficient. It raises the bar from another process on this machine to another process running as this user, and no further, on purpose — because a process already running as you reads ~/.email-agent/accounts/{email}/token.json and calls Gmail directly, and was never going to be stopped by a browser cookie.

The foot-gun, named

A single environment variable, EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1, disarms both halves — the header checks and the whole unlock gate. That is deliberate: an open bind whose guards still demand a local Host would answer 403 to the very browser the open bind exists for.

It does not have to be typed on a command line. The web config loads a repo-root .env before the framework boots, and the example env file ships a commented line for exactly that variable, so a stray .env disarms the gate for the ordinary npm run dev path. Measured against a real dev server with exactly that file and no shell variable: an unauthenticated settings read returned 200 with the settings body, an unauthenticated page load returned 200, and Host: evil.example with no Origin reached the handler. As of August 2026 the process announces this at startup from two independent points, and the CLI prints the same sentences. The silence is fixed; the disarm itself is unchanged and still complete.

§ 09

Six stories, each with a lesson

Not a changelog. These are the ones that teach something.

1. The queue knew the truth. Every screen lied.

The database was correctly recording that an auto-apply had failed after Gmail was already called. No surface read those fields. So the web reported “3 changes await your approval” for rows that were mid-apply, and the CLI printed “nothing was applied” — for mail that really had been trashed. Recording the truth and displaying it are two separate pieces of work, and only the second one is visible to a user.

2. A false sentence in the documentation cost 950 lines of code.

The project’s own notes said the database could not add a column to an existing table. Believing that, someone built a durable-snapshot, cross-process-lock and crash-replay subsystem to survive dropping and rebuilding tables. It was reviewed adversarially twice. Then somebody checked the claim against the installed version: the database can add columns in place. The subsystem was deleted. A wrong sentence in the file everyone reads first outlives, and outcosts, a wrong line of code.

3. Ten rows.

Covered in § 04, and worth repeating as a lesson about testing: it survived because every existing test used fewer than ten rows. Scale is a test condition, not a detail.

4. “The tests pass” was repeatedly false comfort.

Several tests asserted the message a function printed rather than the state of the system, or constructed a request shape the real framework never produces. They were green and they proved nothing. The habit that fixed it: deliberately break the code and confirm the test goes red.

5. And the sequel, which is sharper.

Once the project had component tests, an adversarial re-check went back over five of them with mutations the original authors had not tried: nine mutations, seven went red, two survived. Both survivors were live safety behaviours — the approval panel’s default-deny selection (a row arriving on a background refresh must arrive unticked, or a bulk Apply reaches a change nobody looked at) and the settings banner that reports auto-apply as currently on from the saved value rather than the unsaved switch. Both were documented only in a code comment. The lesson generalises: a test written by the person who wrote the component covers the branches its author was thinking about, so the invariant stated only in a comment is the one left unheld.

6. Two instruction files drifted apart.

The project kept two overlapping documents that had to be edited in parallel by hand. One had been mechanically find-and-replaced into describing files and settings that do not exist, and it still recommended a database call that provably does not work — advice to reintroduce a bug that had stopped mail being stored at all. They are now one file with a check that fails if they are ever separated again.

§ 11

The honest part

A page like this is easy to write as if everything were verified. It is not, and the project treats overclaiming as a defect in its own right, so here is the state plainly — sorted by kind, because “never tested” and “deliberately limited” are not the same admission.

Never observed end to end

There is no linked Gmail account on any machine this has run on

No real mailbox change has ever been observed travelling the whole path. Every apply path in every test ends in a per-operation failure. The claim, the resolution, the reporting and the exit codes are covered; “the trash really reached Gmail” is not, and cannot be from here.

The same limit now applies symmetrically on the read side. No real message read has ever reached Gmail either. In both test harnesses the client throws before any request leaves, so every verification call lands on the credentials residual, and the two verdict branches — a genuine label match or mismatch — are reachable only through core’s own tests with an injected reader.

  • The 404’s three-way meaning, and Gmail’s behaviour when a trashed message is purged, are documented, not observed.
  • The OAuth state guard has never run against Google. The handler half is covered by route-level tests; the consent screen, Google’s echo of the state value, and the browser’s cookie handling across the redirect are verified by reading only.
  • No live gemini invocation. The CLI is installed here and unauthenticated; its output fixtures are derived from source, not observed.
  • No live hosted-model call. Both API executors are driven against a local HTTP stub, so our plumbing is covered but the providers’ acceptance of our request shape, and their error and usage envelopes, are assumed.
  • The 24-hour session lifetime is proven only against an injected clock. Nothing here has sat for a day.
  • The real-browser leg drives exactly one engine, Chromium. The cookie-policy argument for the OAuth redirect is reasoned from spec, not observed in Safari or Firefox.

Rendered by a test, but never seen by a person

These are two different claims and the project keeps them apart on purpose, in this order. Rendered populated under jsdom by an automated test: now true. The approval panel and the stranded panel are driven through the populated queue, the per-email checkboxes, the review dialog, the destructive-change confirmation both ways, the outcome toasts, all six residual reasons and both adjudication buttons — each mutation-checked. Observed populated in a real browser: still false, unchanged, because there is still no Gmail account to populate them with.

And jsdom is not a browser, which should be said once plainly: it has no layout, so a dialog’s focus trap cannot be tested there at all, and its window.confirm is a no-op returning undefined — an unstubbed confirm-gated path silently early-returns and proves nothing. One component, the piece that redeems the unlock token, is not rendered at all: every branch that matters walks into the same navigation API jsdom refuses to let be redefined.

Not covered at all

  • Next itself — routing, middleware, streaming responses, server-component rendering. The harness drives handlers, not the framework.
  • The action runner’s agent half against a real model. The command is driven end to end against a local stub, so the plumbing is covered; nothing in the suite says an LLM would produce that shape.
  • fetch — the sync needs the Gmail API; only its storage half is covered.
  • Small named gaps: the top-level error card on each approval panel, the once-per-mount verify guard’s remount case, and per-card Run/Delete pending state under concurrency.

Deliberate limitation — chosen, not missing

  • The verifier reads the state now and cannot prove this app’s call caused it.
  • The dangerous mirror: an apply that landed and was then undone verifies as not applied and is re-proposed. Idempotent, therefore it cannot destroy anything; it can still undo something you did in between.
  • The read-before-write window is narrowed, never closed. An apply hung past the threshold that then returns from Gmail still loses its outcome — exactly as before this pass existed — and that adjudication can now come from a person or from the automatic verifier. The losing direction is chosen.
  • The stranded count can undercount and never overcount.
  • approvedVia is attribution only: it gates nothing and proves nothing.
  • The apply is serial and stays that way for now. A bounded pool would have to partition by account and message, stay serial inside a partition, wait for retry and backoff, and live strictly inside one chunk.
  • The queue’s duplicate skip is check-then-insert, not a uniqueness guarantee. Two concurrent runs can both insert, and with auto-apply on, Gmail receives both calls.
  • The unlock gate closes exactly one hole and does nothing about code running as this user. The page gate is UX, not enforcement. And one environment variable disarms the whole thing, possibly from a file nobody remembers writing.
  • This design is for one person and one laptop. If it is ever deployed for several people it must be rewritten, not extended — and the ambient-credential sentinel revisited at the same time, because a shared deployment makes it indefensible.

Measured facts with an expiry date

This page trades on measured, not read, so the corollary has to be printed too: every measurement is a fact about an installed version.

  • Every database fact above — the ten-row limit, the pinned handle, in-place column addition, the filter-replacement behaviour — is a fact about one version of LanceDB and must be re-verified on upgrade.
  • The Gmail read timeout works only because the installed HTTP client hands its options verbatim to an implementation that honours them. The next major version would keep the option compiling and silently remove the bound.
  • Credential failures are classified on one specific error field, measured against the installed client. Re-measure on any upgrade.
Where the documentation and the code disagreed

Five disagreements were found by checking prose against source — three while writing this page, two more when it was afterwards fact-checked by someone who had not written it. All five are now fixed. Note the shape of two of the last three: the file-modes and gemini-timing items had been faithfully reproduced from the instruction file, and the instruction file was wrong. Copying an authoritative document accurately is not the same as checking it — the third, credential routing, this page had already gotten right by checking source directly; only the instruction file was self-contradicting.

  • Fixed — and it was on this page until the fact-check found it. The instruction file said every file under ~/.email-agent/ was written 0600 inside 0700. Measured, at the time: only the three credential files were. The mail database was created with no mode and landed 0755/0644, and on a fresh install even the app’s own root directory could land 0755, leaving nothing in the chain shielded. Finding this by fact-checking the prose is what triggered fixing the code, not just the sentence: every directory this app creates is now forced back to 0700 on every write, root to leaf, self-healing a tree an older version left loose. The *.lance table directories LanceDB creates itself stay 0755/0644 — that part of the old claim was never going to become false — and both this page (§ 02) and the instruction file now say so instead of overstating the first part.
  • Fixed — and it was on this page too, until now. The instruction file said an unauthenticated gemini run fails in about four seconds; the executor’s own comment said two, dated and specific (exit code 41, 2026-08-07). This page had faithfully quoted the four, in § 05’s account of the same check. Re-measured 2026-08-22 against the installed CLI directly: 1.17s, same exit code — close enough to corroborate “two” and rule out “four.” Both the instruction file and this page now say two, and both cite the measurement.
  • Fixed. The main instruction file described credential selection as a three-step fallback chain — explicit account, then default account, then ambient credentials. That is not what the code does: an explicit account or a configured default account both resolve through the same function, which throws on missing credentials rather than falling back to anything, and ambient (gcloud ADC) credentials are used only for one explicit sentinel value and one legacy no-accounts-configured case — never as a catch-all after the other two fail. Two hundred lines later the same file already stated the refusal correctly; the summary line now matches it instead of asserting a fallback chain that does not exist.
  • Fixed. A module card said a fragile text-scanning way of reading an action’s id had been eliminated. It had been, in core; the web package still did it. The regular expression is now deleted and both callers share the one parser.
  • Fixed. The web settings form accepted and stored Google client credentials that nothing ever read for authentication — filling it in wrote a secret to disk and left sign-in still failing. The field is gone, and its removal now announces itself once per process when an old settings file still carries it.
§ 12

Everything, in one place

Including the five unrelated things called “token”.

access token
Short-lived proof the app may act on your mailbox now. Expires in about an hour.
ADC
Application Default Credentials — whatever identity gcloud is signed in as. Ambient, and easy to change without noticing.
action
A named prompt run over your mail. Built-in ones ship with the app; you can ask the chat to write more.
AST
Abstract syntax tree — a program as structured data rather than text.
binding token
The second half of a browser session, kept in origin-scoped storage and echoed as a header. Exists because cookies ignore ports.
claim token
An identifier stamped on queue rows when a worker takes them, so it can prove which rows are its own.
commit conflict
The database refusing a write because someone else committed first. Being refused is the safe outcome.
CSRF
Cross-site request forgery — another site making your browser send an authenticated request on your behalf.
DNS rebinding
An attack where a hostile page re-points its own domain at 127.0.0.1 to reach a local service.
embedding
768 numbers representing a text's meaning, arranged so similar texts land near each other.
ESM
The JavaScript module system. Its import evaluates the file, it does not merely read it.
jsdom
A JavaScript implementation of a browser's document API, used to render components in tests. It has no layout and is not a browser.
LanceDB
The embedded vector database used here — a library over files on disk, not a server.
LLM token
A chunk of text as a model counts it, roughly ¾ of a word. Nothing to do with the other four tokens.
loopback
127.0.0.1 — reachable only from this machine. A real boundary, not a header check.
mutation testing
Deliberately breaking the code to confirm a test goes red. A test that cannot fail is not evidence.
MVCC
Multi-version concurrency control. Writers do not lock; a conflicting writer is refused.
monorepo
One repository holding several packages that are released together.
OAuth2
Granting an app narrow, revocable access without sharing your password.
P0–P4
The backlog's priority scale, P0 highest. Not an email priority — that is a separate built-in action.
refresh token
The long-lived credential used to mint access tokens without asking you again.
residual reason
Which of six named things stopped the verification pass from deciding a stranded row, shown so a person can act rather than guess.
scope
The specific permission a grant covers — here, modifying Gmail and nothing else.
session cookie
The half of a browser session the server sets. Shared with every other port on the same host, which is why it is not sufficient alone.
stranded
A queue row left mid-apply by a crash. Email Agent now checks most of them against Gmail itself; what reaches a person is the residual it could not answer.
unlock token
A one-time, ten-minute secret printed on your terminal that opens the web UI in a browser. Burns on first use.
URL fragment
The part of a URL after #. Browsers never send it to a server, which is why the unlock token rides there.
verification pass
The automatic check that reads a stranded row's current Gmail labels before any person is asked about it.
worktree
A second checkout of the same repository, so two branches can be open at once.
