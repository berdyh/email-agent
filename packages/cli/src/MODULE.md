# Module Card: CLI

- purpose: Own Commander entrypoint and command adapters.
- product/module functionality: Fetch emails, manage accounts, run/list actions, review/apply queued Gmail changes (`approvals` command), adjudicate changes stranded mid-apply (`approvals stranded [--review]`), list/restore user action snapshots (`actions snapshots`), serve web UI, manage cron, and read/write config.
- scope boundaries: CLI calls the core barrel export only and should not import core subpaths.
- connected modules/submodules: `@email-agent/core`, setup script, README CLI docs.
- allowed change types: Command flags, help text, argument validation, command-to-core adapter behavior.
- special operating rules: Use `execFile`/`execFileSync` instead of shell-based `exec`; preserve core build-before-CLI typecheck. `approvals review` must record rejections BEFORE applying approvals — the reject never calls Gmail, so it is the half that cannot fail mid-mutation, and applying first discarded the user's per-email "no" answers whenever the apply threw. `run-action` must never prompt to apply anything when `result.applyError` is set: the rows were claimed and Gmail may already have been called, so offering the remainder invites a second trash of mail that is very likely already trashed — it prints core's `describeAutoApplyFailure` verbatim, points at `approvals stranded`, and exits non-zero. `approvals list` reports stranded rows too; they are `applying`, so every other approvals command is blind to them and "no Gmail changes awaiting approval" would otherwise be the only thing a user with an unaccounted-for mutation sees. `approvals stranded` offers exactly two answers and no retry, and its wording never claims the CLI checked Gmail. Nor may it assert WHY a row it listed was not written: core writes only rows still `applying` and past the staleness threshold, so a shortfall can equally mean an apply resolved it, another answer was already recorded, or it was requeued and re-claimed — `strandedSkipReasons` states all three as possibilities, matching the web wording and `describeApplyOutcome`'s precedent. `serve` binds loopback unless `--host` or `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1` says otherwise. `email-lookup.ts` mirrors the web helper: one combined predicate, backticked `accountId`, never chained `.where()`.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: Dotted config writes need typed validation before large config expansion.
- docs that must stay aligned: README CLI section, module index.
- local validation commands/checks: `npx tsc -p packages/cli/tsconfig.json --noEmit`, `email-agent --help` after build.
