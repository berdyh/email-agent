# Module Card: CLI

- purpose: Own Commander entrypoint and command adapters.
- product/module functionality: Fetch emails, manage accounts, run/list actions, review/apply queued Gmail changes (`approvals` command), check Gmail for and adjudicate changes stranded mid-apply (`approvals stranded [--review]`), list/restore user action snapshots (`actions snapshots`), serve web UI, print a one-time link that unlocks the web UI in a browser (`unlock`), manage cron, and read/write config.
- scope boundaries: CLI calls the core barrel export only and should not import core subpaths.
- connected modules/submodules: `@email-agent/core`, setup script, README CLI docs.
- allowed change types: Command flags, help text, argument validation, command-to-core adapter behavior.
- special operating rules: Use `execFile`/`execFileSync` instead of shell-based `exec`; preserve core build-before-CLI typecheck. `approvals review` must record rejections BEFORE applying approvals — the reject never calls Gmail, so it is the half that cannot fail mid-mutation, and applying first discarded the user's per-email "no" answers whenever the apply threw. `run-action` must never prompt to apply anything when `result.applyError` is set: the rows were claimed and Gmail may already have been called, so offering the remainder invites a second trash of mail that is very likely already trashed — it prints core's `describeAutoApplyFailure` verbatim, points at `approvals stranded`, and exits non-zero. `approvals list` reports stranded rows too; they are `applying`, so every other approvals command is blind to them and "no Gmail changes awaiting approval" would otherwise be the only thing a user with an unaccounted-for mutation sees. `approvals stranded` now checks Gmail FIRST (`verifyStrandedApplyingOperations`, gated on a cheap DB read — zero Gmail calls when nothing is stale) and resolves what it can WITHOUT the user; the two human answers and their two-answer, no-retry wording are scoped to what that check could not close — a message gone, this account's credentials not working, the check itself failing, an operation this build cannot classify, or a `""`-account row whose match can never be trusted for the reasons `verify-stranded.ts`'s module header gives. `describeStrandedReason` names WHICH of those SIX a residual row hit — the sixth is `not-checked`, meaning the pass hit `STRANDED_VERIFICATION_DEADLINE_MS` before it reached (or re-read) the row, so nothing was learned and NOTHING WAS TOUCHED; it must not read as a failure, and like `check-failed` the next pass picks it up, whereas `unverifiable-operation` never resolves itself. That budget is why `serve` and `fetch` cannot be stalled by a network that hangs connections rather than resetting them: the worst case is the 20s budget plus the one 10s read that may start just inside it. Nor may it assert WHY a row it listed was not written: core writes only rows still `applying` and past the staleness threshold, so a shortfall can equally mean an apply resolved it, another PERSON already answered it, Email Agent's own automatic verification pass answered it in the meantime, or it was requeued and re-claimed — `strandedSkipReasons` now states FOUR possibilities (the automatic-verification cause is offered separately from another person answering, because a user who pressed nothing cannot guess it exists), matching the web wording and `describeApplyOutcome`'s precedent. `describeStrandedNotifyLines` is the ONE function `fetch` and `serve` both import for their startup/post-fetch notify line, so the wording cannot drift into a third hand-copied string; it returns an empty array when nothing was stale, which is what keeps their happy path silent. Its own `--review` pointer, and `approvals stranded`'s early return, are BOTH gated on core's `strandedRowsRemaining(result)` — never on `result.unresolved.length` alone. A row an in-flight apply re-claims between the verify pass's read and its write is never pushed to `unresolved` (the read succeeded and produced a verdict), but the write can still lose that race and leave the row exactly as stuck as before; gating on `unresolved.length` told a user "None could be resolved automatically" with no `--review` pointer, for a row still sitting in `applying` and unlisted anywhere. When something remains, the command re-reads the live queue rather than trusting the verify pass's own id arrays for row DATA — and that second, later read can itself find nothing (another surface answered it, or the write that raced verify's own adjudicate call finally landed), which prints `describeNothingLeftAfterRecheck()` and exits 0 rather than an empty red header. `describeStrandedListHeader`'s two counts are `explainedCount` (rows the JUST-RUN verify pass actually put in `reasonById`) and `extraCount` (the rest of the re-read list) — the headline is sized off `explainedCount`, never off the raw re-read count, because a row can be listed without ever having been explained by that pass: it went stuck after the pass's own read, or it is exactly the write-lost-its-race row `strandedRowsRemaining` exists to catch. `explainedCount === 0` gets its own sentence rather than "0 Gmail changes Email Agent checked", which would still assert a check happened over these rows. Coverage note: the accounting-gap branch (verify's write losing its race) is unreachable from the CLI e2e harness — there is no linked Gmail account, so every stranded row there lands on the `credentials` residual and `unresolved` is never empty — so that branch is covered only by `verify-stranded.test.ts`'s injected-deps test and `approvals.test.ts`'s direct calls to `strandedRowsRemaining`/`describeStrandedListHeader`; the one-line call sites in the `stranded` command's `.action()` closure are typechecked and reviewed, not exercised by a passing e2e case. `approvals prune` is the ONLY way to see the retention sweep: it otherwise runs as a side effect of the next apply/reject and reports to nobody, and a retention policy nothing can inspect is indistinguishable from data loss. It must keep saying which statuses are never eligible (`pending`/`applying`/`failed`) and must treat 0 days as KEEP FOREVER — `Number("")` is 0 and 0 is the documented opt-out, so reading it as "cutoff = now" would delete the audit trail of the user who most explicitly asked to keep it. `serve` binds loopback unless `--host` or `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1` says otherwise, and now also mints and prints a one-time unlock link BEFORE spawning the Next child (`shouldPrintUnlockUrl`, `unlock-url.ts`) — before, because the child inherits stdio and the parent cannot see its readiness line without switching to pipes and forwarding everything; the printed block says the link works once the server reports ready. It prints NO link when the gate is not running (a non-loopback bind implies the remote flag, and that flag turns the gate off), saying so instead of implying a protection that is not there. `unlock` is the same mint with no server: it exists because the link is one-time and short-lived while a session lapses after a day idle, so without it the only recovery is restarting a server that is working fine — and because `npm run dev`/`npm run start` never reach this package at all, so a contributor on those scripts would meet the unlock screen with no token in existence. It needs no running server and works on one already up, which is precisely why the store is a FILE (`~/.email-agent/session.json`) and not a pair of environment variables handed to the child at spawn: no process can inject an env var into a running child. `unlock` never refuses — with `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1` set in the calling shell it still prints a link, with a note, because that shell says nothing about the environment the server was started in. The batched email lookup is core's `getEmailsByIds` (barrel-exported), NOT a local copy: it used to be duplicated here and in `web/src/modules/api/email-lookup.ts`, and both copies drifted wrong at the same time twice. **NEVER use `rl.question()` for a prompt here.** `readline/promises` settles a pending question only on a `line` event and pauses input between questions, so at EOF — piped input, a redirect, or Ctrl-D mid-review — the promise never settles, commander's action promise hangs and node exits 0 with every decision already collected silently discarded. `prompt.ts` owns every prompt: it drains the interface's async iterator (so buffered lines are delivered and `null` means real EOF) and it attaches a `SIGINT` listener, without which node closes the interface on `^C` and the abort is indistinguishable from EOF. Ctrl-C ABORTS and commits nothing (exit 130); EOF keeps what was decided. A command that asks a question and then hands off to a review loop must thread ONE session through both (`usingPrompt`) — two sequential interfaces over one stdin lose the buffered lines, which is how `printf 'r\ny\nn\n' | email-agent run-action X` silently discarded both review answers. `classifyReviewAnswer`/`classifyStrandedAnswer`/`confirmedYes` decide what an answer means (stop, skip, and No respectively) and are pure so the DEFAULT — anything unrecognised keeps the change queued — is under test.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: Dotted config writes need typed validation before large config expansion.
- docs that must stay aligned: README CLI section, module index.
- test harness: `testing/cli-harness.ts` runs the BUILT `dist/index.js` as a child process against a seeded temp database, which is why `npm test` builds the CLI as well as core — running `src/index.ts` under tsx is cheaper and does not cover the tsc emit, and the emit is what a user runs. Seeding shells out to `core/dist/testing/seed-cli.js` because this package may only import the core barrel. A non-zero exit is an ANSWER, not a spawn failure: several commands exit 1 deliberately.
- local validation commands/checks: `npx tsc -p packages/cli/tsconfig.json --noEmit`, `email-agent --help` after build.
