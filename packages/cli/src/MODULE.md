# Module Card: CLI

- purpose: Own Commander entrypoint and command adapters.
- product/module functionality: Fetch emails, manage accounts, run/list actions, review/apply queued Gmail changes (`approvals` command), check Gmail for and adjudicate changes stranded mid-apply (`approvals stranded [--review]`), list/restore user action snapshots (`actions snapshots`), serve web UI, manage cron, and read/write config.
- scope boundaries: CLI calls the core barrel export only and should not import core subpaths.
- connected modules/submodules: `@email-agent/core`, setup script, README CLI docs.
- allowed change types: Command flags, help text, argument validation, command-to-core adapter behavior.
- special operating rules: Use `execFile`/`execFileSync` instead of shell-based `exec`; preserve core build-before-CLI typecheck. `approvals review` must record rejections BEFORE applying approvals — the reject never calls Gmail, so it is the half that cannot fail mid-mutation, and applying first discarded the user's per-email "no" answers whenever the apply threw. `run-action` must never prompt to apply anything when `result.applyError` is set: the rows were claimed and Gmail may already have been called, so offering the remainder invites a second trash of mail that is very likely already trashed — it prints core's `describeAutoApplyFailure` verbatim, points at `approvals stranded`, and exits non-zero. `approvals list` reports stranded rows too; they are `applying`, so every other approvals command is blind to them and "no Gmail changes awaiting approval" would otherwise be the only thing a user with an unaccounted-for mutation sees. `approvals stranded` now checks Gmail FIRST (`verifyStrandedApplyingOperations`, gated on a cheap DB read — zero Gmail calls when nothing is stale) and resolves what it can WITHOUT the user; the two human answers and their two-answer, no-retry wording are scoped to what that check could not close — a message gone, this account's credentials not working, the check itself failing, an operation this build cannot classify, or a `""`-account row whose match can never be trusted for the reasons `verify-stranded.ts`'s module header gives. `describeStrandedReason` names WHICH of those five a residual row hit — `unverifiable-operation` never resolves itself, `check-failed` may. Nor may it assert WHY a row it listed was not written: core writes only rows still `applying` and past the staleness threshold, so a shortfall can equally mean an apply resolved it, another PERSON already answered it, Email Agent's own automatic verification pass answered it in the meantime, or it was requeued and re-claimed — `strandedSkipReasons` now states FOUR possibilities (the automatic-verification cause is offered separately from another person answering, because a user who pressed nothing cannot guess it exists), matching the web wording and `describeApplyOutcome`'s precedent. `describeStrandedNotifyLines` is the ONE function `fetch` and `serve` both import for their startup/post-fetch notify line, so the wording cannot drift into a third hand-copied string; it returns an empty array when nothing was stale, which is what keeps their happy path silent. `approvals prune` is the ONLY way to see the retention sweep: it otherwise runs as a side effect of the next apply/reject and reports to nobody, and a retention policy nothing can inspect is indistinguishable from data loss. It must keep saying which statuses are never eligible (`pending`/`applying`/`failed`) and must treat 0 days as KEEP FOREVER — `Number("")` is 0 and 0 is the documented opt-out, so reading it as "cutoff = now" would delete the audit trail of the user who most explicitly asked to keep it. `serve` binds loopback unless `--host` or `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1` says otherwise. The batched email lookup is core's `getEmailsByIds` (barrel-exported), NOT a local copy: it used to be duplicated here and in `web/src/modules/api/email-lookup.ts`, and both copies drifted wrong at the same time twice. **NEVER use `rl.question()` for a prompt here.** `readline/promises` settles a pending question only on a `line` event and pauses input between questions, so at EOF — piped input, a redirect, or Ctrl-D mid-review — the promise never settles, commander's action promise hangs and node exits 0 with every decision already collected silently discarded. `prompt.ts` owns every prompt: it drains the interface's async iterator (so buffered lines are delivered and `null` means real EOF) and it attaches a `SIGINT` listener, without which node closes the interface on `^C` and the abort is indistinguishable from EOF. Ctrl-C ABORTS and commits nothing (exit 130); EOF keeps what was decided. A command that asks a question and then hands off to a review loop must thread ONE session through both (`usingPrompt`) — two sequential interfaces over one stdin lose the buffered lines, which is how `printf 'r\ny\nn\n' | email-agent run-action X` silently discarded both review answers. `classifyReviewAnswer`/`classifyStrandedAnswer`/`confirmedYes` decide what an answer means (stop, skip, and No respectively) and are pure so the DEFAULT — anything unrecognised keeps the change queued — is under test.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: Dotted config writes need typed validation before large config expansion.
- docs that must stay aligned: README CLI section, module index.
- test harness: `testing/cli-harness.ts` runs the BUILT `dist/index.js` as a child process against a seeded temp database, which is why `npm test` builds the CLI as well as core — running `src/index.ts` under tsx is cheaper and does not cover the tsc emit, and the emit is what a user runs. Seeding shells out to `core/dist/testing/seed-cli.js` because this package may only import the core barrel. A non-zero exit is an ANSWER, not a spawn failure: several commands exit 1 deliberately.
- local validation commands/checks: `npx tsc -p packages/cli/tsconfig.json --noEmit`, `email-agent --help` after build.
