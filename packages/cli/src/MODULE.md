# Module Card: CLI

- purpose: Own Commander entrypoint and command adapters.
- product/module functionality: Fetch emails, manage accounts, run/list actions, review/apply queued Gmail changes (`approvals` command), adjudicate changes stranded mid-apply (`approvals stranded [--review]`), list/restore user action snapshots (`actions snapshots`), serve web UI, manage cron, and read/write config.
- scope boundaries: CLI calls the core barrel export only and should not import core subpaths.
- connected modules/submodules: `@email-agent/core`, setup script, README CLI docs.
- allowed change types: Command flags, help text, argument validation, command-to-core adapter behavior.
- special operating rules: Use `execFile`/`execFileSync` instead of shell-based `exec`; preserve core build-before-CLI typecheck. `approvals review` must record rejections BEFORE applying approvals — the reject never calls Gmail, so it is the half that cannot fail mid-mutation, and applying first discarded the user's per-email "no" answers whenever the apply threw. `run-action` must never prompt to apply anything when `result.applyError` is set: the rows were claimed and Gmail may already have been called, so offering the remainder invites a second trash of mail that is very likely already trashed — it prints core's `describeAutoApplyFailure` verbatim, points at `approvals stranded`, and exits non-zero. `approvals list` reports stranded rows too; they are `applying`, so every other approvals command is blind to them and "no Gmail changes awaiting approval" would otherwise be the only thing a user with an unaccounted-for mutation sees. `approvals stranded` offers exactly two answers and no retry, and its wording never claims the CLI checked Gmail. Nor may it assert WHY a row it listed was not written: core writes only rows still `applying` and past the staleness threshold, so a shortfall can equally mean an apply resolved it, another answer was already recorded, or it was requeued and re-claimed — `strandedSkipReasons` states all three as possibilities, matching the web wording and `describeApplyOutcome`'s precedent. `serve` binds loopback unless `--host` or `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1` says otherwise. `email-lookup.ts` mirrors the web helper: one combined predicate, backticked `accountId`, never chained `.where()`, and an explicit `limit(UNLIMITED_QUERY_ROWS)` — LanceDB caps an unlimited query at 10 rows. **NEVER use `rl.question()` for a prompt here.** `readline/promises` settles a pending question only on a `line` event and pauses input between questions, so at EOF — piped input, a redirect, or Ctrl-D mid-review — the promise never settles, commander's action promise hangs and node exits 0 with every decision already collected silently discarded. `createAnswerReader` drains the interface's async iterator instead and returns `null` at EOF; `classifyReviewAnswer`/`classifyStrandedAnswer`/`confirmedYes` decide what that means (stop, skip, and No respectively) and are pure so the DEFAULT — anything unrecognised keeps the change queued — is under test.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: Dotted config writes need typed validation before large config expansion.
- docs that must stay aligned: README CLI section, module index.
- test harness: `testing/cli-harness.ts` runs the BUILT `dist/index.js` as a child process against a seeded temp database, which is why `npm test` builds the CLI as well as core — running `src/index.ts` under tsx is cheaper and does not cover the tsc emit, and the emit is what a user runs. Seeding shells out to `core/dist/testing/seed-cli.js` because this package may only import the core barrel. A non-zero exit is an ANSWER, not a spawn failure: several commands exit 1 deliberately.
- local validation commands/checks: `npx tsc -p packages/cli/tsconfig.json --noEmit`, `email-agent --help` after build.
