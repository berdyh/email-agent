# Module Card: Core Actions

- purpose: Own email action contracts, discovery, user action source files, action execution, and Gmail operation mapping.
- product/module functionality: Built-in and user-created actions can be listed, loaded, run against emails, persisted as results, and mapped to Gmail write operations that are queued for explicit user approval.
- scope boundaries: Does not own Gmail auth/fetch, DB schema, web UI, or CLI presentation. Calls those modules through exported functions only.
- connected modules/submodules: `agents` for model execution, `db/actions` for result persistence, `gmail/operations` for writes, web `/api/actions*`, CLI `run-action` and `list-actions`.
- allowed change types: Action type contract changes, registry/runner behavior, user action path validation, built-in action additions, operation mapping.
- special operating rules: User action filenames must pass `user-action-paths.ts`. USER ACTION FILES ARE NEVER EXECUTED: `loadUserAction()` and `ActionRegistry`'s `ACTIONS_DIR` pass read the file and call `extractActionData()` (`action-source-guard.ts`), which statically evaluates it and returns the action object without the file entering the module graph. Do not reintroduce `import()` — or the `new Function("p", "return import(p)")` bundler escape hatch — on that path; only `registry.ts`'s built-in directory may import, because those files are in-repo and reviewed. That is enforced BEHAVIOURALLY by `load-path-denied.test.ts`, which writes genuinely malicious `.action.ts`/`.action.js` files (whose top level writes a marker file, proven to execute under a native import) into a temp actions directory, loads them through the real `loadUserAction()` and `ActionRegistry.loadAll()`, and asserts the marker was never written — an assertion re-spelling cannot defeat. The AST scan in `action-source-guard.test.ts` is a fast TRIPWIRE alongside it, not a proof: it only recognises loader calls whose callee it enumerates, so it catches the two regressions that happened and makes no claim beyond that. Do not restate it as covering any spelling. There is exactly ONE reader of `ACTIONS_DIR` — `readUserActionFiles()` in `user-actions.ts` — and `listUserActions()`, `loadUserAction()` and `ActionRegistry` all go through it, so an action file has ONE identity; a second reader is how a file came to list under one id and load under another. The directory is a parameter defaulting to `ACTIONS_DIR`, which is what makes the behavioural test possible at all. THE EXTRACTED VALUE MUST MATCH WHAT NODE WOULD PRODUCE, not merely be inert: a named export is a live binding read at the end of the walk, `export default` snapshots its operand, `mod.default ?? mod.action` coalesces on the value, and any file Node would reject with `SyntaxError` is refused rather than evaluated (`reserved-binding`, `duplicate-declaration`, `duplicate-export` — `parseDiagnostics` is a syntax pass and does not see strict-mode early errors). Where the evaluator cannot model a construct, it refuses; it must never return a best guess. `extractActionData()` is deliberately stricter than the loaders it replaced in one place — `id`/`name`/`prompt` must be non-empty strings, not merely truthy — and reports that through `onDiagnostic`, which both loaders wire to `console.warn`. Gmail operations should carry `accountEmail` when derived from stored emails; `applyOperations()` uses operation-level account identity before any batch fallback. APPROVAL GATE: `ActionRunner` must never call `applyOperations()` directly — it enqueues via `approval.ts` and mutations only run through `applyPendingOperationsByIds()` after the user approved them (web approvals panel or CLI prompt/`approvals` command). The one exception is the opt-in `gmail.autoApplyActions` setting, which applies the batch right after enqueueing; it requires `gmail.autoApplyAcknowledged`, enforced in `config/settings.ts`, so never read the toggle without going through `loadSettings()`. ORDERING: the `action_results` row is written BEFORE its queue rows, because queue rows are stamped `batchId = resultId` and would otherwise reference a batch that was never recorded; if that write fails, queueing is skipped entirely. ERROR FIELDS ARE NOT INTERCHANGEABLE: `queueError` means a strictly pre-Gmail failure (nothing was applied), `applyError` means auto-apply threw after the rows were claimed and Gmail may already have been mutated — never report the second as the first. ADOPTED BY BOTH SURFACES: `applyError`, `persistError` and `duplicateOperations` are read by `describeActionRunOutcome` (`packages/web/src/modules/api/action-run-contract.ts`, rendered by `app/actions/page.tsx`) and `describeRunOutcome` (`packages/cli/src/commands/run-action.ts`). Both print `describeAutoApplyFailure`/`describeUnrecordedBatchFailure` VERBATIM rather than composing their own copy, and on `applyError` neither reports the batch as awaiting approval nor prompts to apply anything — those rows are `applying`, not `pending`, which is exactly the bug the split fixed. `adjudicateStrandedOperations(ids, "applied" | "notApplied", { olderThanMs, now })` closes out a row `getStaleApplyingOperations()` lists: it claims by token AND re-asserts the staleness cutoff in the same write predicate, so neither a row an apply already resolved nor one an apply claimed inside the threshold can be touched. `options.evidence` says where the answer came from — a person (`"user-confirmed"`, the default, stamping `STRANDED_APPLIED_NOTE`) or a Gmail label read-back (`"verified-api"`, stamping `STRANDED_VERIFIED_NOTE`) — and it picks the note and the `resolutionEvidence` column TOGETHER, so the sentence a human reads and the value a machine reads cannot drift apart. The requeue branch clears the evidence for both answers. THE WINDOW THAT REMAINS, which every description of this must state: an apply hung past the threshold that later returns loses its outcome — its write-back matches nothing, `resolveClaimedOperations` warns, and after a `notApplied` answer the change can reach Gmail a second time behind an audit trail saying it never happened. The alternative (hung apply wins) would leave the user unable to close out a row they checked, so the losing direction is deliberate. The count it returns is read after the write and may undercount, never overcount; a shortfall has three possible causes (an apply resolved it, another adjudication answered it, it was requeued and re-claimed) and no surface may assert one of them — and the second now has TWO flavours a surface should offer separately, another person or an automatic verification pass, because a user who pressed nothing cannot guess the second exists. `verifyStrandedApplyingOperations()` (`verify-stranded.ts`) answers what it can WITHOUT the user: the cheap stale-list read FIRST (an empty queue costs zero Gmail calls, which is what lets it run unprompted), then one `messages.get` per row SERIALLY through the injected reader, then `verdictFromLabels` — the whole predicate table, pure, read off `gmail/operations.ts` (`spam` needs SPAM present AND INBOX ABSENT because `markAsSpam` is one atomic modify; `trash` needs TRASH present ALONE because Gmail drops INBOX implicitly), then a SECOND SERIAL READ PASS OVER THE REQUEUE CANDIDATES ONLY (re-reading the applied set buys nothing and spends quota — see limit 3 below), then TWO adjudications over disjoint id sets. Both passes share one `classifyRow` and one `recordApplied`; a second copy of either would drift, and the drift in `recordApplied` would be a route around the `""` refusal. It FAILS CLOSED to the human path, never to a verdict, for an empty label list (`[].every(...)` is true and `applyOperations` throws for those), an unknown type, a 404 (THREE-WAY AMBIGUOUS — deleted, an ADC row now pointing elsewhere, or a trash/spam that WORKED and was purged), an auth failure, and any error from the check itself; residual rows carry which of `message-missing`/`credentials`/`check-failed`/`unverifiable-operation`/`unscoped-account` they hit, because "we could not check" is not actionable. A row with `accountId: ""` is checked but may NEVER resolve to `applied`: `createGmailClient("")` resolves whatever ADC points at now, and unlike the apply path (where a wrong mailbox 404s harmlessly) a wrong mailbox on the READ path could retire the row on evidence from another account. IT IS NOT RECOVERY and offers no retry: it records an end state or hands the row to a person. THREE LIMITS THAT CANNOT BE ENGINEERED AWAY: it reads the state NOW and cannot prove this app's call caused it (a message the user archived by hand verifies applied — end state right, attribution wrong, benign); the MIRROR of that, an apply that landed and was then UNDONE by the user verifies notApplied and is re-proposed, which is the direction that can produce a SECOND mutation — a re-apply cannot destroy anything (no send, no permanent delete, no counter) but it can undo something the user did in between, so "idempotent, therefore harmless" is the wrong sentence; and the read-before-write window, NARROWED on 2026-08-21 and never closed — only its `notApplied` direction was ever a defect (labels the check saw present were present, so a late apply agrees with an `applied` record; a stale `notApplied` requeues a change that has now happened and a later approval can send it again), so requeue candidates are re-read immediately before the write, while Gmail landing between THAT read and the write remains irreducible, because an external system and a local database cannot be read and written atomically. A candidate that flips to `applied` on the re-read passes the same `""` refusal (mutation-checked: deleting the one guard fails all four ADC tests); a re-read that FAILS never falls back to the first read. None of it can be closed by claiming first, since a crash between claim and release would re-stamp `claimedAt` and hide the row for another threshold. Surfaces: `StrandedOperationsPanel` + `/api/approvals/stranded` (web), `approvals stranded [--review]` (CLI). What IS now covered, added by the surfaces wave: `POST /api/approvals/stranded/verify` is driven through the real route handler over a real temp-directory LanceDB (`approvals.route.test.ts`) — the cheap-gate `checked: 0` case, the no-linked-account residual classification (pinned as `credentials`, not assumed), and that a row claimed moments ago by a healthy apply is left untouched; `email-agent approvals stranded` is driven through the BUILT binary the same way. What is STILL NOT covered: the applied/requeued VERDICT branches (a genuine label match or mismatch) are unreachable from either surface's harness, because both run with no linked Gmail account and every verify call there lands on the `credentials` classification before it can reach `verdictFromLabels` — that logic's own 19 cases in `verify-stranded.test.ts` are the only coverage of it. React component rendering (`StrandedOperationsPanel` firing the check once per mount, the toast, the id-joined per-row reason) remains unverified: no component testing library exists in this repo (M3 adds one). See TODOS.md, "THE SURFACES WAVE" item 3 and "Integration harness for the approval gate". `applyPendingOperationsByIds()` CLAIMS, applies and resolves in chunks of `APPLY_RESOLUTION_CHUNK_SIZE` (10), with the claim INSIDE the loop (`applyClaimedOperationsInChunks`) so the claimed set and the in-flight set coincide: a crash or DB failure strands at most one chunk of THAT CALL in `applying`, and every id it has not reached is still `pending`, so it stays approvable and rejectable. The bound is per call, not per batch: two concurrent applies leapfrog (A claims ids 1-10 and calls Gmail; B loses those, continues, and claims 11-20 while A is in flight), so a crash strands one chunk per in-flight caller. Pinned by a regression test in `approval.test.ts`. Do NOT hoist the claim back out of the loop — claiming the whole batch up front bounded the mutated-but-unrecorded set to one chunk but left the *entire remainder* stranded on a first-chunk failure. Each chunk mints its own claim token, because resolution predicates are scoped to `claimToken` AND `status`. A failure to record a chunk aborts the rest of the batch rather than continuing to mutate mail whose fate cannot be written down. `applyOperations()` is barrel-private: `actions/index.ts` must never export it (nor may any public specifier reach it), as defense in depth against a by-name import from any workspace-resolvable context — web bundling, any future in-tree loading. That privacy is NO LONGER load-bearing for user actions (they are parsed, never imported, so they cannot import anything either); keep it anyway as the cheap loud failure for an in-tree caller. Only `approval.ts` calls it, via relative import, on claimed rows. A regression test (`barrel-surface.test.ts`) pins this. Generated source is also gated at save time by `assertSafeActionSource()`, called from `saveUserAction()` before anything touches disk, so the model gets a 422 it can act on. Save-time and load-time share ONE traversal — `findActionSourceViolations()` is `analyzeActionSource()` with the extracted values discarded — and they must stay that way; a second, parallel evaluator would drift and the drift would be a bypass. It is an allowlist over the TypeScript AST (`typescript` is a runtime dependency of core for this, and is listed in web's `serverExternalPackages` so it is not bundled): only type-only imports/exports, type declarations, static-data variable statements and `export default` are permitted, so a file that passes contains no construct capable of executing. Keep it AST-based — the original text-scanning version was defeated by `({}).constructor.constructor("return process")()`, which names the Function constructor without spelling it, and the payload hid in a string the scanner had already blanked. APPLY STAYS SERIAL, one Gmail round trip per operation, and `applyOperations()` returns exactly one outcome per input operation IN ORDER because `toOperationOutcomes` pairs them positionally with the claimed rows. `messages.batchModify` is REJECTED, not pending, on two grounds read off its REST reference (2026-08-07): its success response body is empty, so it reports no per-message result and N rows would collapse onto one all-or-nothing status — the ambiguity `toOperationOutcomes` deliberately fails closed on — and one request is one `ids[]` list against one `addLabelIds`/`removeLabelIds` pair under one `userId`, so only identical (account, addLabelIds, removeLabelIds) tuples could share a call and a junk batch (trash + spam + archive interleaved) is three distinct tuples that fragment into single-operation calls anyway. It is NOT rejected for being unable to express `trash`; an earlier revision asserted that and it was false. `TRASH` is a manually-appliable system label (unlike `SENT`/`DRAFT`) and `batchModify` restricts `addLabelIds` only by the 1000-id cap, so `addLabelIds: ["TRASH"]` is the batched equivalent of `messages.trash()`, exactly as `markAsSpam()` already uses `modify` + `["SPAM"]`. `batchDelete` is the analogue of `messages.delete` (permanent) and must never be substituted for trash, but that is not a ground against `batchModify`. A bounded pool is deferred, not refused; if it is built it must partition by (account, message) and stay serial inside a partition (several pending operations can target one message, and serial order is the order the user reviewed), it must land after retry/backoff exists (a failure here is terminal — a `failed` row is not `pending`, so an approved change is dropped until the action is re-run), and it must live strictly INSIDE one chunk, since a pool spanning chunks would put two chunks in flight and undo the reason the claim sits in the loop. A queue row's `accountId` of `""` is replayed at approval time as gcloud ADC and never as a configured default account, so it may address a different mailbox than the one the message was read from; the observable result is a 404 recorded as a `failed` row rather than a wrong-mailbox mutation, but that is a property of Gmail's per-mailbox id space, not a guard here. Named-account rows cannot be affected.
- current stubs/placeholders: None known; user actions are parsed rather than imported, guarded by filename/path validation and the pure-data allowlist.
- irrelevant or incomplete code to remove/rework: None known. The regex metadata extraction is gone — it was a second reader of the action id, and its disagreement with the parsed id made a listed action unloadable; listing now comes from the same static evaluation the loader uses. Web's save route (`POST /api/actions/user`) also stopped keeping its own regex reader of the id for its pre-write built-in-conflict check — a const-bound id (`const ID = "junk"; export default { id: ID, ... }`) resolved correctly by this module's evaluator but not by that regex, so a shadowing file saved without tripping the conflict check. The route now calls `extractActionData()` for that check too, so an action file has one identity at the point it is first accepted, not just at the point it is later loaded.
