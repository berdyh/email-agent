# Module Card: Core Actions

- purpose: Own email action contracts, discovery, user action source files, action execution, and Gmail operation mapping.
- product/module functionality: Built-in and user-created actions can be listed, loaded, run against emails, persisted as results, and mapped to Gmail write operations that are queued for explicit user approval.
- scope boundaries: Does not own Gmail auth/fetch, DB schema, web UI, or CLI presentation. Calls those modules through exported functions only.
- connected modules/submodules: `agents` for model execution, `db/actions` for result persistence, `gmail/operations` for writes, web `/api/actions*`, CLI `run-action` and `list-actions`.
- allowed change types: Action type contract changes, registry/runner behavior, user action path validation, built-in action additions, operation mapping.
- special operating rules: User action filenames must pass `user-action-paths.ts`. USER ACTION FILES ARE NEVER EXECUTED: `loadUserAction()` and `ActionRegistry`'s `ACTIONS_DIR` pass read the file and call `extractActionData()` (`action-source-guard.ts`), which statically evaluates it and returns the action object without the file entering the module graph. Do not reintroduce `import()` — or the `new Function("p", "return import(p)")` bundler escape hatch — on that path; only `registry.ts`'s built-in directory may import, because those files are in-repo and reviewed. That is enforced BEHAVIOURALLY by `load-path-denied.test.ts`, which writes genuinely malicious `.action.ts`/`.action.js` files (whose top level writes a marker file, proven to execute under a native import) into a temp actions directory, loads them through the real `loadUserAction()` and `ActionRegistry.loadAll()`, and asserts the marker was never written — an assertion re-spelling cannot defeat. The AST scan in `action-source-guard.test.ts` is a fast TRIPWIRE alongside it, not a proof: it only recognises loader calls whose callee it enumerates, so it catches the two regressions that happened and makes no claim beyond that. Do not restate it as covering any spelling. There is exactly ONE reader of `ACTIONS_DIR` — `readUserActionFiles()` in `user-actions.ts` — and `listUserActions()`, `loadUserAction()` and `ActionRegistry` all go through it, so an action file has ONE identity; a second reader is how a file came to list under one id and load under another. The directory is a parameter defaulting to `ACTIONS_DIR`, which is what makes the behavioural test possible at all. THE EXTRACTED VALUE MUST MATCH WHAT NODE WOULD PRODUCE, not merely be inert: a named export is a live binding read at the end of the walk, `export default` snapshots its operand, `mod.default ?? mod.action` coalesces on the value, and any file Node would reject with `SyntaxError` is refused rather than evaluated (`reserved-binding`, `duplicate-declaration`, `duplicate-export` — `parseDiagnostics` is a syntax pass and does not see strict-mode early errors). Where the evaluator cannot model a construct, it refuses; it must never return a best guess. `extractActionData()` is deliberately stricter than the loaders it replaced in one place — `id`/`name`/`prompt` must be non-empty strings, not merely truthy — and reports that through `onDiagnostic`, which both loaders wire to `console.warn`. Gmail operations should carry `accountEmail` when derived from stored emails; `applyOperations()` uses operation-level account identity before any batch fallback. APPROVAL GATE: `ActionRunner` must never call `applyOperations()` directly — it enqueues via `approval.ts` and mutations only run through `applyPendingOperationsByIds()` after the user approved them (web approvals panel or CLI prompt/`approvals` command). The one exception is the opt-in `gmail.autoApplyActions` setting, which applies the batch right after enqueueing; it requires `gmail.autoApplyAcknowledged`, enforced in `config/settings.ts`, so never read the toggle without going through `loadSettings()`. ORDERING: the `action_results` row is written BEFORE its queue rows, because queue rows are stamped `batchId = resultId` and would otherwise reference a batch that was never recorded; if that write fails, queueing is skipped entirely. ERROR FIELDS ARE NOT INTERCHANGEABLE: `queueError` means a strictly pre-Gmail failure (nothing was applied), `applyError` means auto-apply threw after the rows were claimed and Gmail may already have been mutated — never report the second as the first. NOT YET ADOPTED: `applyError`, `persistError` and `duplicateOperations` are populated here but no surface reads them (the web result type in `use-actions.ts` declares only `queueError`). Be precise about what happens instead, because on an auto-apply failure `queueError` is UNSET: `packages/web/src/app/actions/page.tsx` falls through to its "N changes await your approval" branch and reports rows that are now `applying`, and `packages/cli/src/commands/run-action.ts` queries `status: "pending"` for the batch and prints "nothing was applied" only when that comes back empty (a single-chunk abort) — a multi-chunk abort leaves later ids pending, so it prompts to apply those and never mentions the chunk that may already have hit Gmail. Different routes, same wrong outcome — neither surface tells the user that mail may really have been trashed. The fields and the wording helpers (`describeAutoApplyFailure`, `describeUnrecordedBatchFailure`) exist; the fix does not until the adoption pass in TODOS.md lands. `applyPendingOperationsByIds()` CLAIMS, applies and resolves in chunks of `APPLY_RESOLUTION_CHUNK_SIZE` (10), with the claim INSIDE the loop (`applyClaimedOperationsInChunks`) so the claimed set and the in-flight set coincide: a crash or DB failure strands at most one chunk of THAT CALL in `applying`, and every id it has not reached is still `pending`, so it stays approvable and rejectable. The bound is per call, not per batch: two concurrent applies leapfrog (A claims ids 1-10 and calls Gmail; B loses those, continues, and claims 11-20 while A is in flight), so a crash strands one chunk per in-flight caller. Pinned by a regression test in `approval.test.ts`. Do NOT hoist the claim back out of the loop — claiming the whole batch up front bounded the mutated-but-unrecorded set to one chunk but left the *entire remainder* stranded on a first-chunk failure. Each chunk mints its own claim token, because resolution predicates are scoped to `claimToken` AND `status`. A failure to record a chunk aborts the rest of the batch rather than continuing to mutate mail whose fate cannot be written down. `applyOperations()` is barrel-private: `actions/index.ts` must never export it (nor may any public specifier reach it), as defense in depth against a by-name import from any workspace-resolvable context — web bundling, any future in-tree loading. That privacy is NO LONGER load-bearing for user actions (they are parsed, never imported, so they cannot import anything either); keep it anyway as the cheap loud failure for an in-tree caller. Only `approval.ts` calls it, via relative import, on claimed rows. A regression test (`barrel-surface.test.ts`) pins this. Generated source is also gated at save time by `assertSafeActionSource()`, called from `saveUserAction()` before anything touches disk, so the model gets a 422 it can act on. Save-time and load-time share ONE traversal — `findActionSourceViolations()` is `analyzeActionSource()` with the extracted values discarded — and they must stay that way; a second, parallel evaluator would drift and the drift would be a bypass. It is an allowlist over the TypeScript AST (`typescript` is a runtime dependency of core for this, and is listed in web's `serverExternalPackages` so it is not bundled): only type-only imports/exports, type declarations, static-data variable statements and `export default` are permitted, so a file that passes contains no construct capable of executing. Keep it AST-based — the original text-scanning version was defeated by `({}).constructor.constructor("return process")()`, which names the Function constructor without spelling it, and the payload hid in a string the scanner had already blanked. APPLY STAYS SERIAL, one Gmail round trip per operation, and `applyOperations()` returns exactly one outcome per input operation IN ORDER because `toOperationOutcomes` pairs them positionally with the claimed rows. `messages.batchModify` is REJECTED, not pending: it reports no per-message result, so N rows would collapse onto one all-or-nothing status — the ambiguity `toOperationOutcomes` deliberately fails closed on — it cannot express `trash` (`batchDelete` is permanent deletion and must never be substituted), and only identical (account, addLabelIds, removeLabelIds) tuples could share a call. A bounded pool is deferred, not refused; if it is built it must partition by (account, message) and stay serial inside a partition (several pending operations can target one message, and serial order is the order the user reviewed), it must land after retry/backoff exists (a failure here is terminal — a `failed` row is not `pending`, so an approved change is dropped until the action is re-run), and it must live strictly INSIDE one chunk, since a pool spanning chunks would put two chunks in flight and undo the reason the claim sits in the loop. A queue row's `accountId` of `""` is replayed at approval time as gcloud ADC and never as a configured default account, so it may address a different mailbox than the one the message was read from; the observable result is a 404 recorded as a `failed` row rather than a wrong-mailbox mutation, but that is a property of Gmail's per-mailbox id space, not a guard here. Named-account rows cannot be affected.
- current stubs/placeholders: None known; user actions are parsed rather than imported, guarded by filename/path validation and the pure-data allowlist.
- irrelevant or incomplete code to remove/rework: None known. The regex metadata extraction is gone — it was a second reader of the action id, and its disagreement with the parsed id made a listed action unloadable; listing now comes from the same static evaluation the loader uses.
- docs that must stay aligned: `CREATE_ACTION_SKILLS.md`, `EDIT_ACTION_SKILLS.md`, web action cards, CLI action commands, `docs/architecture/module-index.md`.
- local validation commands/checks: `npm test -- packages/core/src/actions/*.test.ts`, `npx tsc -p packages/core/tsconfig.json --noEmit`, `npm run check:boundaries`.
