# Module Card: Core Config

- purpose: Own runtime settings, defaults, filesystem paths, prompt defaults, and account config types.
- product/module functionality: Load/save settings, expose defaults consumed by core, web, CLI, and setup, and own the unlock-token + session store behind the local web UI (`session.ts`). The gate's on/off flag and its disarmed-run warning live next door in `../unlock-gate/` and are re-exported by `session.ts`.
- scope boundaries: Does not own setup UX, Gmail OAuth implementation, or per-route request validation.
- connected modules/submodules: All core modules, web settings API, CLI config/setup, `setup.sh`. `session.ts` additionally has three callers that must agree on one spelling: `email-agent serve`/`email-agent unlock` (mint), the web API guard layer (validate), and the web page gate (validate).
- allowed change types: Config type additions, defaults, settings persistence helpers.
- special operating rules: New config fields must be added to `setup.sh` templates if fresh installs need them. The auto-apply consent invariant — `gmail.autoApplyActions` is forced false unless `gmail.autoApplyAcknowledged` is true — has ONE implementation, `normalizeAutoApplyConsent`, which `normalizeSettings` calls; every writer must go through `loadSettings`/`saveSettings` so no path can enable unattended Gmail mutations without acknowledgement. The web API boundary enforces the same rule a second time on purpose (defense in depth) and must CALL that export rather than keep its own copy — `normalizeGmailConfig` in `packages/web/src/modules/api/validation.ts` is still a duplicate, tracked in TODOS.md. Dotted-path config writes go through `setNestedConfigValue`/`getNestedConfigValue` (`config/dotted-path.ts`), which refuse `__proto__`/`constructor`/`prototype` in any position; that is hygiene rather than a live fix (the pollution route is currently shadowed by the own properties `normalizeSettings` always writes), and the CLI still uses its own private copies, also tracked. A removed settings key whose loss changes behaviour should announce itself: `gmail.syncActions` warns once per path per process from `loadSettingsFromPath`, guarded both by the parse-on-cache-miss and by a warned-paths set, because `loadSettings()` re-reads the file on every call and anything hung off the read would print per request. `loadSettings()` READS `SETTINGS_PATH` on every call and caches only the parse, keyed on a sha256 of the bytes it read; do NOT reintroduce an unconditional cache, and do NOT re-key it on file metadata, because `gmail.autoApplyActions` is a kill switch and a stale copy keeps mutating Gmail after the user turned it off. `mtimeMs + size` was tried and is not file identity (a restore, `git checkout` or `rsync --times` reproduces the mtime, and equal-length settings files are easy to produce) — the staleness was reproduced against a built `dist`. Hashing the bytes actually read also removes the TOCTOU between `stat()` and `readFile`. That per-call re-read is load-bearing rather than belt-and-braces: Next.js does NOT guarantee one module instance per process (verified from a production build — `app/api/auth/callback/route.js` carries its own inlined copy of this module, separate from the shared chunk `/api/settings` writes through), so `clearSettingsCache()` only clears the caller's own copy and cannot be the invalidation mechanism. `loadSettings()` also fails CLOSED: ENOENT is the ONLY condition under which "no settings file, use defaults" is a fact, and every other errno plus an unparsable file throws with the errno and the path. Absence of information must never read as permission to destroy data — `retention.approvalQueueDays` governs pruning of resolved `pending_operations` rows, the default is 365 days while the explicit opt-out is 0, and the sweep in `actions/approval.ts` reads it, so a momentarily unreadable file used to delete audit rows a user had explicitly opted out of pruning. A non-positive value disables pruning, and the default is deliberately generous because the rows are an audit trail of real Gmail mutations.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: Arbitrary dotted-path writes in CLI config should move behind typed validation before broad settings expansion; the first step exists (`config/dotted-path.ts`) and is waiting for the CLI to adopt it.
- docs that must stay aligned: README environment/setup sections, `setup.sh`, CLI config docs.
- session store rules: `session.ts` is file-backed state under `~/.email-agent/session.json`, and it is ALL SYNCHRONOUS on purpose — the web guards return `Response | undefined` and roughly twenty route files call them without `await`. It persists sha256 DIGESTS only, never a plaintext token or cookie value, which is what makes a same-user-readable file an acceptable channel at all. It now reads NO environment variable at all — a test asserts that — because the gate's one off switch moved to `../unlock-gate/index.ts` (`isUnlockGateEnabled`, re-exported from here so no importer changed). That module reads exactly ONE variable, `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS`, and there is deliberately no "arming" variable: `next.config.ts` loads the repo-root `.env` into the web process, so any unlock variable read here could be armed by a stale committed value nobody printed. The gate is therefore ON unless that flag says otherwise, whichever command started the server. The split is not cosmetic: this file imports `node:crypto`/`node:fs`, and Next's instrumentation hook — which is what makes `npm run dev`/`npm run start` announce a disarmed gate — is bundled for the edge runtime too, where a chain reaching those builtins fails to compile. Keep the re-export; do not move the flag back. `exchangeUnlockToken` performs its whole rate-check/compare/burn/mint sequence with NO `await` inside it — that is what makes a double exchange impossible on one event loop, and a test fails if an `await` appears there. Read paths fail CLOSED on an unusable store (nobody is authenticated); `mintUnlockToken` fails OPEN onto a fresh store, because it is the recovery command and throwing would leave a locked-out user with no way back in. Across processes the store is an unlocked read-modify-write, so a `unlock` mint racing a session write can lose one update — documented, not defended against; writes are whole-file renames, so no reader ever sees a partial store. Everything under `~/.email-agent/` is written through `shared/private-files.ts` (`0700` dir, `0600` file). The cookie's `Max-Age` (`SESSION_COOKIE_MAX_AGE_SECONDS`, a year) is deliberately NOT the session TTL: `Max-Age` is browser-enforced from the moment the cookie is set and nothing re-sets it, so matching the two would delete the cookie after a day and make the idle renewal dead code; the store is the sole authority, and a cookie whose record has expired matches nothing. `parseStore` validates the `unlock` record as strictly as the arrays — valid JSON is not a valid store, and an `unlock` of the wrong shape used to reach the digest compare and throw, turning the documented `invalid` into a 500.
- local validation commands/checks: `npx tsc -p packages/core/tsconfig.json --noEmit`, `npx tsc -p packages/cli/tsconfig.json --noEmit`.
