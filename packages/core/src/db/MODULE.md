# Module Card: Core DB

- purpose: Own LanceDB connection, Arrow schemas, table helpers, query filters, and embedding generation.
- product/module functionality: Store emails, action results, clusters, and pending Gmail operations awaiting user approval; generate embeddings used for similarity/clustering.
- scope boundaries: Does not own Gmail fetch/account logic, action execution, or web route parsing. Does not own threads (no thread table/helpers — deleted as dead code).
- connected modules/submodules: `gmail/sync`, `actions/runner`, `analysis/clusterer`, web API routes.
- allowed change types: Schema updates, query helpers, escaping/filter builders, embedding provider calls.
- special operating rules: LanceDB string filters must escape user values; camelCase fields in filters need backticks; never use `add(..., { mode: "overwrite" })`; use `mergeInsert` or scoped delete/update plus append; email row identity is `accountId` + Gmail `id`, where empty `accountId` is the legacy/gcloud sentinel; unread reconciliation updates only same-account stale unread rows; `pending_operations` rows are append + status-update only (pending → applying → applied/failed/rejected) so approved/rejected batches remain an audit trail; the ONLY deletion path is `prunePendingOperations()`, which may touch `applied`/`rejected` rows past the retention window and must never touch `pending`, `applying` or `failed`. `claimedAt` records when a row left `pending` and is the age basis for `getStaleApplyingOperations()`, which LISTS rows a crash stranded mid-apply and does nothing else — it is a report, not a recovery, and it has no caller yet. **Schema migrations add columns IN PLACE and never drop a table.** `migrateSchema()` in `db/connection.ts` probes each table with `missingColumns()` and calls `ensureTableColumns()` (`db/migrations.ts`), which uses `Table.addColumns()` — present in `@lancedb/lancedb` 0.15.0, verified 2026-08-07 against the installed native binary on a real table with rows in every status. To add a column: put the field in that table's Arrow schema in `connection.ts` and an SQL sentinel in its `*ColumnDefaults` map, where the sentinel must produce exactly what a fresh insert writes (a migrated `pending_operations` row therefore comes back queued and unclaimed); a column with no declared sentinel throws rather than being filled with NULL. Do NOT reintroduce read → drop → create → re-insert: it came from a since-deleted comment claiming LanceDB has no ALTER TABLE, it loses every row if the process dies after the drop, and the 975-line snapshot/lock/replay subsystem written to survive that has been deleted rather than hardened. All four tables (`emails`, `action_results`, `clusters`, `pending_operations`) use the one path; `emails` included, so cached embeddings are not thrown away. Concurrency needs no lock: `addColumns`/`createEmptyTable` are single MVCC commits, the loser fails loudly, and `ensureTableColumns` re-probes the table's current schema before accepting the winner's commit.
- current stubs/placeholders: Local embeddings use deterministic hashed token vectors at the fixed LanceDB vector dimension. `PendingOperationRecord.claimedAt` is declared optional purely so the web/CLI fixtures keep compiling; the Arrow column is non-nullable.
- irrelevant or incomplete code to remove/rework: None known.
- docs that must stay aligned: Gmail sync card, module index, setup/docs for embedding provider.
- local validation commands/checks: `npm test -- packages/core/src/gmail/sync-records.test.ts`, `npx tsc -p packages/core/tsconfig.json --noEmit`.
