# Module Card: Core DB

- purpose: Own LanceDB connection, Arrow schemas, table helpers, query filters, and embedding generation.
- product/module functionality: Store emails, action results, clusters, and pending Gmail operations awaiting user approval; generate embeddings used for similarity/clustering.
- scope boundaries: Does not own Gmail fetch/account logic, action execution, or web route parsing. Does not own threads (no thread table/helpers — deleted as dead code).
- connected modules/submodules: `gmail/sync`, `actions/runner`, `analysis/clusterer`, web API routes.
- allowed change types: Schema updates, query helpers, escaping/filter builders, embedding provider calls.
- special operating rules: A LanceDB `Table` HANDLE IS PINNED TO THE VERSION IT WAS OPENED AT (verified on a real table against 0.15.0, 2026-08-07: a handle advances only through its own writes, a stale handle's `query()` silently returns old rows and its `update()` THROWS `Commit conflict`, `checkoutLatest()` refreshes in place — and CONFIRMED ACROSS TWO OS PROCESSES by `db/cross-process-claim.race.test.ts`, which forks two node processes over one directory and races them for three rows six rounds: exactly one owner every round, zero rows claimed twice, the raw loser refused with `Commit conflict for version N`, the winner alternating. THE LOSER GETS AN ERROR, NOT A NO-OP: `updateAtLatestVersion` is what converts it into the silent zero-rows-won the claim protocol assumes, so any write that must lose a race quietly has to go through it — an AST case in that test fails if a `table.update()` is added to `pending-operations.ts` outside the wrapper. `db/emails.ts` and `db/clusters.ts` deliberately take the raw error; they are single-write non-queue paths where a failed request the user can repeat is the right outcome) — every multi-step read/write sequence here goes through `updateAtLatestVersion`/`queryAtLatestVersion`, which refresh first and retry a conflict on a bounded ladder, or a sequence meant to lose a race quietly explodes instead. **EVERY UNBOUNDED SCAN MUST PASS `limit(UNLIMITED_QUERY_ROWS)`** (`db/utils.ts`): LanceDB applies a DEFAULT LIMIT OF 10 to a plain FILTERED query, not just to vector searches (measured on a 25-row table against 0.15.0, 2026-08-07 — `countRows()` said 25, `query().where(...).toArray()` said 10; `limit(0)` is zero rows, not "no limit"). Without it the approval queue listed at most 10 changes, a claim's read-back-by-token was capped at 10, and the mail list ignored the caller's own limit. Pinned by `db/query-limit.test.ts`. **`mergeInsert` DOES NOT WORK ON THESE TABLES — do not reach for it.** Two independent reasons, both measured on a real table against 0.15.0: `createEmptyTable(name, schema)` builds NON-NULLABLE columns (apache-arrow's `Field` defaults `nullable=false`) while LanceDB infers `nullable=true` from plain JS objects, and `mergeInsert` refuses the mismatch where `table.add()` coerces; and the join key is composed as `target_<key>` and parsed as an UNQUOTED SQL identifier, so a camelCase key like `accountId` folds to `target_accountid` and fails, with no escape (backticks make it worse). `upsertEmails` is therefore delete-then-append over a predicate GROUPED BY ACCOUNT — `accountId IN (a,b) AND id IN (p,q)` is a cross product that would delete pairs the batch never named. LanceDB string filters must escape user values; camelCase fields in filters need backticks; never use `add(..., { mode: "overwrite" })`; use scoped delete/update plus append;  email row identity is `accountId` + Gmail `id`, where empty `accountId` is the legacy/gcloud sentinel, and EXACTLY ONE ROW PER THAT PAIR IS EXPECTED — an invariant that is stated at `emailSchema` in `db/connection.ts` and UPHELD BY ONE WRITER, not enforced: LanceDB has no primary key and no unique constraint, so nothing rejects a second row for a pair, and `upsertEmails` deleting the pairs it is about to write is the whole of the enforcement. Anything that appends to `emails` without deleting the pair first breaks it silently, because no read errors — a duplicate just makes one row win. `getEmailsByIds` therefore does not assume uniqueness: it picks the newest `date` deterministically instead of whichever row the scan reached last (a property of the scan, not of the data, so the same table could answer differently on two calls). `date` is the RAW RFC-2822 `Date:` header, so that comparison must PARSE — lexical and chronological order disagree ("Fri, 1 Jan 2027" sorts before "Mon, 2 Feb 2026") — with an unparseable header ranked below any real timestamp and a genuine tie keeping the incumbent; unread reconciliation updates only same-account stale unread rows; `pending_operations` rows are append + status-update only (pending → applying → applied/failed/rejected) so approved/rejected batches remain an audit trail; the ONLY deletion path is `prunePendingOperations()`, which may touch `applied`/`rejected` rows past the retention window and must never touch `pending`, `applying` or `failed`. `approvedVia` (`"web"` | `"cli"` | `"auto-apply"` | `""`) records which surface claimed a row — written by `claimPendingOperations()`, a REQUIRED parameter with no default, `values`-only and never in a `where` predicate, so the claim's atomic write predicate is unchanged. It is ATTRIBUTION ONLY: it gates nothing and proves nothing, because there is no unforgeable in-process caller identity to derive it from (ESM module identity is process-global). `""` means unclaimed-or-legacy and must never be guessed onto a row that lacks it — the migration sentinel is `CAST('' AS STRING)`, and a sentinel that guessed a plausible surface (say `'web'`) would fabricate an audit record nobody observed. `adjudicateStrandedOperations` clears it back to `""` only on a `notApplied` answer; the `applied` branch deliberately leaves it, so a stranded row keeps recording which surface initiated the crashed apply. `claimedAt` records when a row left `pending` and is the age basis for `getStaleApplyingOperations()`, which LISTS rows a crash stranded mid-apply and does nothing else — a report, not a recovery. Its callers are `GET /api/approvals/stranded` and `email-agent approvals stranded`. The only way such a row leaves `applying` is `resolveStrandedApplyingOperations()`, which is claim-then-write: a token is stamped on rows `buildStrandedClaimFilter(ids, cutoffIso)` matches — `applying` AND older than the staleness cutoff, both clauses inside the one atomic write — then read back, then the final state is written scoped to that token, and the count is a SECOND read taken after that write (the post-claim read over-reported when a concurrent adjudication stole the token). The age clause is not decoration: the surfaces filter their LISTS by age but submit bare ids, and a JS pre-filter would leave a window between the age test and the destructive token stamp. It can UNDERCOUNT (a requeued row re-claimed before the count read) but never overcount. WHAT IT DOES NOT COVER, and must not be described as covering: an apply hung past the threshold that later returns still loses its outcome — its write-back is scoped to the token this overwrote, so `resolveClaimedOperations` matches nothing, reads back by token, and WARNS naming the rows; on a `notApplied` answer the change can then reach Gmail a second time. That direction is chosen deliberately over stranding a user with a row they have checked and cannot close. It records what the USER reports about Gmail and verifies nothing; there is deliberately no retry. **Schema migrations add columns IN PLACE and never drop a table.** `migrateSchema()` in `db/connection.ts` probes each table with `missingColumns()` and calls `ensureTableColumns()` (`db/migrations.ts`), which uses `Table.addColumns()` — present in `@lancedb/lancedb` 0.15.0, verified 2026-08-07 against the installed native binary on a real table with rows in every status. To add a column: put the field in that table's Arrow schema in `connection.ts` and an SQL sentinel in its `*ColumnDefaults` map, where the sentinel must produce exactly what a fresh insert writes (a migrated `pending_operations` row therefore comes back queued and unclaimed); a column with no declared sentinel throws rather than being filled with NULL. Do NOT reintroduce read → drop → create → re-insert: it came from a since-deleted comment claiming LanceDB has no ALTER TABLE, it loses every row if the process dies after the drop, and the 953-line snapshot/lock/replay subsystem written to survive that has been deleted rather than hardened. All four tables (`emails`, `action_results`, `clusters`, `pending_operations`) use the one path; `emails` included, so cached embeddings are not thrown away. Concurrency needs no lock: `addColumns`/`createEmptyTable` are single MVCC commits, the loser fails loudly, and `ensureTableColumns` re-probes the table's current schema before accepting the winner's commit. It does, however, need to tolerate a table another process is still committing — `tableNames()` enumerates the on-disk `*.lance` directories, so a name is LISTED before its `_versions/1.manifest` exists and `openTable()` rejects it in that window with `Table 'X' was not found`, the same message a table that never existed produces. Every `openTable` on the migration path therefore goes through `openCommitted()`, which retries ONLY while the name is still listed (the listing is the sole evidence separating "mid-create" from "absent") and is bounded at 1/2/5/10/25/50/100/200ms; an absent name or a non-"not found" error is rethrown on the first attempt, and exhausting the ladder throws rather than hanging or pretending the table is fine. This is a product invariant, not a test concern: `cron setup` firing while `serve` starts, or two overlapping CLI commands, really do call `initDb()` concurrently, and `initPromise` only serializes callers inside one process. `action_results.accountId` uses `""` for BOTH a legacy/gcloud-ADC row and an all-accounts run whose emails spanned several accounts, so account-filtered history cannot represent a genuine multi-account run; that is deliberate for now, because `getActionResults`'s `accountId` option has no caller (the one reader filters by `actionId` alone) and a `mixed` marker would still not surface such a run under either account, while per-account rows would break `batchId = action_results row id`. Revisit when a surface first passes `accountId`, and reach for an `accountIds` array column rather than a third sentinel. The batched approval-surface lookup lives HERE as `getEmailsByIds` (with `emailRefKey`, `buildEmailLookupFilter` and the `EmailLookupTable` seam). It was previously duplicated in `web/src/modules/api/email-lookup.ts` and `cli/src/email-lookup.ts`, hand-copied `escapeSql` and all, and both copies went wrong together twice — `limit(refs.length)`, then no limit at all behind a comment falsely asserting LanceDB's default limit is vector-only. Its scan is explicitly `UNLIMITED_QUERY_ROWS` and the predicate is what bounds it. `action_results.tokensUsed` is total tokens processed — all input (cached at full weight) + all output, work not money, `0` meaning "not reported" — and rows written before 2026-08-07 carry the old per-executor measurements and are not comparable with newer ones.
- current stubs/placeholders: Local embeddings use deterministic hashed token vectors at the fixed LanceDB vector dimension.
- irrelevant or incomplete code to remove/rework: None known.

- test fixtures: `src/testing/` is test-only (not on the barrel, not in the package `exports` map). `lancedb-fixture.ts` is THE way to test against a real database — it redirects `$HOME`, re-reads `LANCEDB_DIR` and throws if the result is not inside the temp directory, so a test whose core import is hoisted above the swap fails loudly instead of writing to the developer's real `~/.email-agent`. Seeding goes through the product's own write paths. `seed-cli.js` is the same fixture as a subprocess entry point, for the CLI tests (which may only import the core barrel). `claim-race-worker.ts` is one side of the two-process claim race.
