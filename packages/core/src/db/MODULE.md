# Module Card: Core DB

- purpose: Own LanceDB connection, Arrow schemas, table helpers, query filters, and embedding generation.
- product/module functionality: Store emails, action results, clusters, and pending Gmail operations awaiting user approval; generate embeddings used for similarity/clustering.
- scope boundaries: Does not own Gmail fetch/account logic, action execution, or web route parsing. Does not own threads (no thread table/helpers — deleted as dead code).
- connected modules/submodules: `gmail/sync`, `actions/runner`, `analysis/clusterer`, web API routes.
- allowed change types: Schema updates, query helpers, escaping/filter builders, embedding provider calls.
- special operating rules: LanceDB string filters must escape user values; camelCase fields in filters need backticks; never use `add(..., { mode: "overwrite" })`; use `mergeInsert` or scoped delete/update plus append; email row identity is `accountId` + Gmail `id`, where empty `accountId` is the legacy/gcloud sentinel; unread reconciliation updates only same-account stale unread rows; `pending_operations` rows are append + status-update only (pending → applying → applied/failed/rejected) so approved/rejected batches remain an audit trail; the ONLY deletion path is `prunePendingOperations()`, which may touch `applied`/`rejected` rows past the retention window and must never touch `pending`, `applying` or `failed`. `claimedAt` records when a row left `pending` and is the age basis for `getStaleApplyingOperations()`, which LISTS rows a crash stranded mid-apply and does nothing else — a report, not a recovery. Its callers are `GET /api/approvals/stranded` and `email-agent approvals stranded`. The only way such a row leaves `applying` is `resolveStrandedApplyingOperations()`, which is claim-then-write (token stamped on still-`applying` rows, read back, final state scoped to that token) so an apply that has since recorded a real outcome is never overwritten with the user's guess, and is scoped by `buildStrandedClaimFilter` to `applying` alone. It records what the USER reports about Gmail and verifies nothing; there is deliberately no retry. **Schema migrations add columns IN PLACE and never drop a table.** `migrateSchema()` in `db/connection.ts` probes each table with `missingColumns()` and calls `ensureTableColumns()` (`db/migrations.ts`), which uses `Table.addColumns()` — present in `@lancedb/lancedb` 0.15.0, verified 2026-08-07 against the installed native binary on a real table with rows in every status. To add a column: put the field in that table's Arrow schema in `connection.ts` and an SQL sentinel in its `*ColumnDefaults` map, where the sentinel must produce exactly what a fresh insert writes (a migrated `pending_operations` row therefore comes back queued and unclaimed); a column with no declared sentinel throws rather than being filled with NULL. Do NOT reintroduce read → drop → create → re-insert: it came from a since-deleted comment claiming LanceDB has no ALTER TABLE, it loses every row if the process dies after the drop, and the 953-line snapshot/lock/replay subsystem written to survive that has been deleted rather than hardened. All four tables (`emails`, `action_results`, `clusters`, `pending_operations`) use the one path; `emails` included, so cached embeddings are not thrown away. Concurrency needs no lock: `addColumns`/`createEmptyTable` are single MVCC commits, the loser fails loudly, and `ensureTableColumns` re-probes the table's current schema before accepting the winner's commit. It does, however, need to tolerate a table another process is still committing — `tableNames()` enumerates the on-disk `*.lance` directories, so a name is LISTED before its `_versions/1.manifest` exists and `openTable()` rejects it in that window with `Table 'X' was not found`, the same message a table that never existed produces. Every `openTable` on the migration path therefore goes through `openCommitted()`, which retries ONLY while the name is still listed (the listing is the sole evidence separating "mid-create" from "absent") and is bounded at 1/2/5/10/25/50/100/200ms; an absent name or a non-"not found" error is rethrown on the first attempt, and exhausting the ladder throws rather than hanging or pretending the table is fine. This is a product invariant, not a test concern: `cron setup` firing while `serve` starts, or two overlapping CLI commands, really do call `initDb()` concurrently, and `initPromise` only serializes callers inside one process. `action_results.accountId` uses `""` for BOTH a legacy/gcloud-ADC row and an all-accounts run whose emails spanned several accounts, so account-filtered history cannot represent a genuine multi-account run; that is deliberate for now, because `getActionResults`'s `accountId` option has no caller (the one reader filters by `actionId` alone) and a `mixed` marker would still not surface such a run under either account, while per-account rows would break `batchId = action_results row id`. Revisit when a surface first passes `accountId`, and reach for an `accountIds` array column rather than a third sentinel. `action_results.tokensUsed` is total tokens processed — all input (cached at full weight) + all output, work not money, `0` meaning "not reported" — and rows written before 2026-08-07 carry the old per-executor measurements and are not comparable with newer ones.
- current stubs/placeholders: Local embeddings use deterministic hashed token vectors at the fixed LanceDB vector dimension. `PendingOperationRecord.claimedAt` is declared optional purely so the web/CLI fixtures keep compiling; the Arrow column is non-nullable.
- irrelevant or incomplete code to remove/rework: None known.
- docs that must stay aligned: Gmail sync card, module index, setup/docs for embedding provider.
- local validation commands/checks: `npm test -- packages/core/src/gmail/sync-records.test.ts`, `npx tsc -p packages/core/tsconfig.json --noEmit`.
