# Module Card: Core Gmail

- purpose: Own Gmail auth/accounts, client creation, message fetch/parsing, sync orchestration, and write operations.
- product/module functionality: Fetch emails into LanceDB, resolve account identity, support multi-account OAuth, and execute Gmail mutations.
- scope boundaries: Does not own DB schema beyond record mapping, action decisions, or web/CLI presentation.
- connected modules/submodules: `config`, `db`, `actions/apply`, web Gmail routes, CLI fetch/accounts/cron.
- allowed change types: OAuth/account management, fetch parsing, sync mapping, write operations.
- special operating rules: Write operations (`operations.ts`) AND the raw client factories (`createGmailClient`, `createGmailClientForAccount` — they return a gmail.modify-scoped googleapis client, so they are the mutation surface too) are barrel-private — `gmail/index.ts` must never re-export them and the package `exports` map must not expose a path to them, so no by-name import from a workspace-resolvable context can mutate Gmail past the approval queue. This is defense in depth, not the enforcement boundary: user action files no longer execute at all (they are parsed by `actions/action-source-guard.ts`, never imported), so the barrel privacy now guards against in-tree callers and future loading paths rather than against a user action. Core imports them relatively; web's manual mail actions use the webpack-only `@email-agent/core/gmail/operations` tsconfig path (unresolvable by Node at runtime, sole-consumer-enforced by `check-module-boundaries.mjs`). `barrel-surface.test.ts` pins source barrels, dist barrels, and the `exports`-map key allowlist. The label READER (`read.ts`, `readMessageLabels` — `users.messages.get` with `format: "minimal"`, for verifying a stranded apply) is barrel-private too, for a DIFFERENT reason: it cannot change anything, but it hands back mailbox content keyed by message id. It is deliberately NOT in `operations.ts` and NOT in that test's `deniedNames`, which is derived from `Object.keys(gmailOps)` and means "this writes"; a separate case asserts its absence instead. Its `accountEmail` is REQUIRED and takes `""` verbatim, so a queue row's ADC sentinel can never be checked against the configured default account, and its failure classification tests `err.status`, NOT `err.code` (measured against the installed gaxios 6.7.1: `status` comes from the HTTP response and `code` only from a transport error) — re-measure on any googleapis upgrade. IT IS ALSO BOUNDED IN TIME, and the bound is not where you would guess: `timeout` is declared in gaxios 6.7.1's `common.d.ts:104` and NEVER READ anywhere in `gaxios.js`, working only because `common.js:66` picks node-fetch 2.7.0 when there is no `window` and passes the options through verbatim — gaxios 7 drops node-fetch for the platform `fetch`, which ignores `timeout`, so the option would keep compiling while the bound vanished. `getMessageLabels` therefore sends `{ timeout: GMAIL_REQUEST_TIMEOUT_MS (8s), retryConfig: { noResponseRetries: 0 } }`; the retry override is REQUIRED because `googleapis-common/apirequest.js:263` defaults `retry: true` and a bare `timeout: T` costs ~3T (measured 2026-08-22: T=800 -> 3,013ms, vs 802ms with the override), and it suppresses only no-response retries so 429/5xx keep theirs. `readMessageLabels` then wraps the WHOLE read in `GMAIL_READ_DEADLINE_MS` (10s), OUTSIDE the getter's credential catch, because the request timeout does not cover building the client (an OAuth refresh has no timeout of its own and the `""` ADC path shells out to `gcloud` through `execFile`, which has none either) and because a deadline must classify as `error` -> `check-failed`, never as `noCredentials` telling a user their Google access is broken. Both are proved against a `node:http` stub that accepts and never responds (`read.test.ts`, each test carrying an explicit `node:test` timeout and the stub calling `closeAllConnections()`); a test that only asserted the option was PASSED would pass against a client that ignores it. `accountEmail?: string` must continue threading through fetch/write paths; account removal/default changes reset cached clients. Sync must fetch with the resolved account identity before reconciling unread rows so fallback Gmail clients cannot be mixed with stored account rows. `createGmailClient` throws for a named account with missing/invalid stored credentials — it does not fall back to gcloud ADC. ADC is only used for the explicit empty-string account id and for the unscoped/no-accounts-configured path. That matters for queued approvals: a `pending_operations` row carrying `accountId: ""` is replayed through `createGmailClient("")` whenever the user approves it, which resolves ADC AT THAT MOMENT — so if ADC has been re-pointed since the message was read, the row is applied against a different mailbox, and (message ids being per-mailbox) the observable result is a 404 recorded as a `failed`, terminal row rather than a mutation of the wrong mail. Nothing here verifies the identity matches; see `recordToGmailOperation` in `actions/approval.ts` for the full statement. The web OAuth callback URI is derived from the request origin, so EVERY origin the app is served on must be a registered authorized redirect URI in the Google Cloud console (README documents this; `serve --port N` is what made it origin-derived). `listAccounts()` has no try/catch: it propagates whatever `loadSettings()` throws rather than swallowing it into `[]`. That policy lives in exactly one place (`loadSettings()`'s ENOENT-only fail-closed rule) and must not be re-implemented here with a narrowed catch — the non-ENOENT errors it throws are plain `Error`s with the errno in the message, not a `.code` a catch could branch on. Callers already handle the throw: CLI `accounts list` prints it and exits 1, `GET /api/accounts` answers 500.
- current stubs/placeholders: Embedding failure fallback stores deterministic local vectors; complete unread syncs reconcile stale local unread rows without table overwrite; explicit empty account ids route to gcloud ADC.
- irrelevant or incomplete code to remove/rework: None known.
- docs that must stay aligned: README Gmail/setup sections, CLI accounts docs, module index.
- local validation commands/checks: `npm test -- packages/core/src/gmail/*.test.ts`, `npx tsc -p packages/core/tsconfig.json --noEmit`.
