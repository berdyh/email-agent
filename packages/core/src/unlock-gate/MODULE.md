# Module Card: Unlock Gate Switch

- purpose: Own the single environment flag that disarms the browser unlock gate, the one wording for saying so, and the once-per-process announcement that says it.
- product/module functionality: `isUnlockGateEnabled(env)` (the gate is ON unless `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1`), `UNLOCK_GATE_DISABLED_LINES` (the shared wording), `warnIfUnlockGateDisabled(env, log)` (prints at most once per process, returns whether it printed).
- scope boundaries: Owns no state, no I/O and no crypto. The unlock token, the session store and the cookie contract all live in `../config/session.ts`, which re-exports these three so no existing importer had to change.
- connected modules/submodules: `core/config/session.ts` (re-export), the web API guard layer (`packages/web/src/modules/api/validation.ts` — every read of the flag in the web process goes through its `remoteAccessAllowed()`, which calls the warning), `packages/web/src/modules/api/unlock-gate-notice.ts` and through it `packages/web/src/instrumentation.ts` (Next's server-startup hook), `packages/cli/src/unlock-url.ts` (`describeUnlockDisabledLines()` returns the shared lines), `email-agent serve`, `email-agent unlock`.
- allowed change types: Wording changes to the disabled block; nothing that adds state, I/O, a dependency or a second environment variable.
- special operating rules: **NOTHING in this module may import a `node:` builtin, or anything that transitively does.** That is not stylistic. `packages/web/src/instrumentation.ts` is compiled by Next for the EDGE runtime as well as the node one, and webpack traces its dynamic import chain in BOTH — a `process.env.NEXT_RUNTIME !== "nodejs"` early return does not prevent it. While the chain reached `config/session.ts` (which imports `node:crypto` and `node:fs`), every `next dev` start printed `⨯ node:crypto  Module build failed: UnhandledSchemeError` (measured 2026-08-22 against Next 15.5.19; `next build` survived it with a warning). `unlock-gate.test.ts` fails if an import appears here. **The once-per-process flag lives on `globalThis` under `Symbol.for("email-agent.unlock-gate-disabled-warned")`, never a module-level boolean** — Next does not guarantee one module instance per process, and since the instrumentation split this module is duplicated across BUNDLES too (the startup hook's bundle and the route bundles each carry a copy). The registry symbol is the only thing they share, and it is what makes them warn once between them rather than once each; a test imports a genuinely second instance (`./index.js?copy=2`) and fails if they disagree. **This module reads exactly ONE environment variable and there must never be a second**, in either direction: an "arming" variable could be armed by a stale repo-root `.env` (`packages/web/next.config.ts` loads one before Next boots) with no token anybody printed, and a second disarming variable would be a second silent off switch. The warning must keep naming the repo-root `.env` and `next.config.ts` — the measured way into this state is a file the user never typed into, copied from the commented line in `.env.example`.
- current stubs/placeholders: None.
- irrelevant or incomplete code to remove/rework: None.
- docs that must stay aligned: AGENTS.md's unlock-gate and "Local-only enforcement" bullets, `packages/core/src/config/MODULE.md`, `packages/web/src/modules/api/MODULE.md`, `.env.example`, README environment section.
- local validation commands/checks: `npx tsc -p packages/core/tsconfig.json --noEmit`, `node --import tsx --test packages/core/src/unlock-gate/unlock-gate.test.ts`, `npm run check:boundaries`.
