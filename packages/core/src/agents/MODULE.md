# Module Card: Core Agents

- purpose: Own model/CLI executor contracts and fallback routing.
- product/module functionality: Route prompts to Claude SDK/CLI, Codex, Gemini, OpenRouter, or direct API; stream real incremental chunks for executors that support it (Claude SDK/CLI today), with a genuine one-shot fallback for executors that don't.
- scope boundaries: Does not own action prompts, analysis prompt content, settings storage, or UI transport.
- connected modules/submodules: `config` for routing settings, `actions` and `analysis` as callers, web action generation route.
- allowed change types: Executor adapters, availability checks, fallback order, streaming behavior, environment cleanup for nested CLI calls.
- special operating rules: CLI executor flags are provider-specific; preserve known Codex/Claude spawn rules from project instructions. The barrel (`index.ts`) only exports the shared types and `AgentRouter` — individual executor classes (`ClaudeExecutor`, `CodexExecutor`, `GeminiExecutor`, `DirectApiExecutor`, `OpenRouterExecutor`, `SdkExecutor`) are constructed internally by `router.ts` via relative imports and are not part of the public barrel; do not re-add those re-exports without a real external consumer.
- **`tokensUsed` invariant:** every executor MUST report the same measurement — **total tokens processed = all input (cached counted at full weight) + all output**. `tokens.ts` is the single source of that definition and owns the per-provider normalizers; new executors call one of them rather than doing their own arithmetic. The arithmetic differs per provider because they disagree on whether cached input is *included in* or *additional to* `input_tokens`: Anthropic's `input_tokens` is the uncached remainder so `cache_creation_input_tokens`/`cache_read_input_tokens` are **additive**, while codex's `cached_input_tokens` is a **subset** of `input_tokens` and must not be added. Getting that backwards is what made the column incomparable. `0` means "not reported", never "free".
- **Parsing is pure and testable:** CLI stdout parsing lives in exported pure functions (`parseClaudeCliOutput`, `parseCodexOutput`, `parseGeminiOutput`) so token accounting and text extraction can be unit-tested without spawning a CLI. Keep new CLI executors to that shape — several of these CLIs cannot be run in CI (gemini needs interactive browser OAuth).
- **API executors take an injectable `baseURL`/`apiKey`/`model`** (defaults unchanged) purely so they can be driven against a local `node:http` stub. Do not remove that seam — it is the only way these paths are covered without spending money.
- current stubs/placeholders: A single non-streaming chunk is the contract when `AgentRouter.executeStream()` calls an executor without `executeStream()`, or when streaming fails before emitting any chunk.
- irrelevant or incomplete code to remove/rework: The codex legacy `msg`/`token_count` envelope branch has never been observed on a live run (codex-cli 0.145.0 emits no `msg` wrapper); it is an unverified best-effort fallback for older CLIs.
- **`isAvailable()` must answer "can this run a prompt?", not "is the binary installed?"** `GeminiExecutor.isAvailable()` probed `--version` alone, so on a machine with the CLI installed and never signed in it returned true; the router then selected gemini and the CLI blocked on an interactive browser consent screen until the 120s `execFile` timeout — one dead run per attempt, reported as a timeout. It now also requires credential material (`geminiCredentialSource`, whose locations were read out of the installed `@google/gemini-cli` 0.54.4), and `execute()` spawns with `NO_BROWSER=1` so an unauthenticated run fails in seconds with a message naming the fix. Neither proves the credentials WORK — only a real call can — and that limit is stated at the function.
- known-unverified: the gemini execute path has never produced a SUCCESSFUL run end to end — its parse fixtures are derived from the installed CLI's own source and shipped docs, not a live answer. What has been observed live on this machine (2026-08-07) is the unauthenticated failure: `NO_BROWSER=1` turns a 120s hang into a ~4s `FatalAuthenticationError` (exit 41), and `isAvailable()` now returns false in 0ms. Neither API executor has ever made a live provider call.
- docs that must stay aligned: README agent system, module index, setup docs for supported CLIs.
- local validation commands/checks: `npx tsc -p packages/core/tsconfig.json --noEmit`, focused tests when executor parsing changes.
