# Module Card: Web Actions Components

- purpose: Own action list, generated-action chat, edit flow, and user-action append controls.
- product/module functionality: Let users browse built-ins, create/edit user actions, save generated source, run actions, and review/approve queued Gmail changes (`approval-panel.tsx`: per-email checkboxes, click-to-read dialog, apply/reject), let Email Agent check Gmail for, and adjudicate what remains of, changes a crash stranded mid-apply (`StrandedOperationsPanel`, same file), and restore a previous version of a user action (`snapshot-restore-dialog.tsx`).
- scope boundaries: Does not write files directly or execute actions; all persistence/execution goes through API routes.
- connected modules/submodules: `hooks/use-actions`, `hooks/use-approvals`, `modules/api/action-run-contract`, `modules/api/approvals-contract`, `modules/api/snapshot-contract`, `hooks/use-action-snapshots`, `hooks/use-action-chat`, `store/action-chat-store`, `/api/actions*`, `/api/approvals*`, core actions.
- allowed change types: Action UI state, chat rendering, save/edit UX, action card composition.
- special operating rules: Do not render empty assistant streaming placeholders; preserve filename display/edit contract. There IS a component testing library now (vitest + React Testing Library; `.test.tsx` beside the component, patterns in `src/testing/MODULE.md`), and `snapshot-restore-dialog.tsx`, `approval-panel.tsx`'s `ApprovalPanel` and its `StrandedOperationsPanel` are ALL rendered by one now (`approval-panel.test.tsx`, `stranded-operations-panel.test.tsx`) — keep the wording and the request shaping in `modules/api/*-contract.ts` and the hooks, which are tested, and let the component pick a layout and call them. A component test asserts WHICH wording the component picked for the state it is in; it must not re-pin strings the contract's own test already pins. `snapshot-restore-dialog.tsx` in particular must surface a refused restore as the specific rules the snapshot broke (`describeSnapshotRestoreFailure`), never as a generic failure toast: the CLI has always printed them, and a user whose action was overwritten has nothing else to act on. `StrandedOperationsPanel` fires `useVerifyStranded()` (`POST /api/approvals/stranded/verify`) EXACTLY ONCE per mount, guarded by a ref rather than an effect dependency on the query result — `useStrandedApprovals()` refetches in the background (window focus, another mutation's invalidation), and any of those re-firing the mutation would turn a one-time Gmail check into the polling loop this repo deliberately does not have. The verify result's `unresolved` rows are joined to the GET list's rows BY ID, not trusted as exhaustive: a row can go stale after this mount's one check ran, and a row absent from that join renders an honest "not checked this session" line rather than an invented reason (`stranded-operations-panel.test.tsx`'s "six reasons" test carries a seventh, unlisted row to cover exactly this). Header and confirm-dialog copy must say Email Agent CHECKED and could not resolve automatically, never that it "cannot check" — the two buttons are now scoped to residual rows only, and both `describeResidualReason`'s SIX cases (`message-missing`, `credentials`, `check-failed`, `unverifiable-operation`, `unscoped-account`, `not-checked`) and `strandedSkipReasons`'s four causes (automatic verification stated SEPARATELY from another person answering) must stay in step with the CLI's copies in `commands/approvals.ts`. Only the "applied" branch of `handleResolve`'s confirmation embeds the row's reason text (`Email Agent could not resolve this automatically: ${reasonText}`) — the "notApplied" branch's confirmation does not mention the reason at all; a test asserting the reason appears in the confirm dialog must click "I checked Gmail — it happened", not "it didn't". The header/description themselves come ENTIRELY from `describeStrandedPanelCopy(strandedPanelStatus(verify), opts)` (`modules/api/approvals-contract.ts`) — the component only computes `explainedCount` (how many of the live list's rows have a `residualById` entry) and passes it through; it must never branch on `verify.isSuccess`/`isPending` itself, because that two-way branch is exactly what let a failed check keep claiming present tense "is checking...now" forever (the panel's once-per-mount guard means a failed verify never retries this session) — `stranded-operations-panel.test.tsx`'s check-failed test is mutation-checked directly against this: reintroducing the dropped-`isError` wiring at the `strandedPanelStatus(verify)` call site turns it red. Also rendered and mutation-checked: the two toast paths never merge — `describeVerifyResolution` (Email Agent's own automatic Gmail read, fired once on mount) is a different claim than `describeStrandedResolution` ("on your word", fired only when a human clicks one of the two adjudication buttons), and each test computes its expectation by calling the function the code path is supposed to use.
