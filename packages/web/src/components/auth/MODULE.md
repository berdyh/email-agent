# Module Card: Web Auth Components

- purpose: Own the client-side half of the unlock flow — the `#token=…` fragment handoff and the static recovery screen.
- product/module functionality: `unlock-exchange.tsx` is mounted by `/unlock` when the link carries the non-secret `?exchange=1` marker (the root `page.tsx` dispatcher no longer handles the token at all — it only decides cookie → `/mail`, else → `/unlock`). It reads the token from the URL FRAGMENT (`location.hash`), not a query param — the fragment is never sent to a server, which is what keeps `next dev`'s request logger from printing it — and scrubs it via `history.replaceState` BEFORE the network round trip (the token has already done its job by reaching the browser; nothing is served by leaving it visible while a fetch is in flight). It POSTs the token to `POST /api/auth/unlock`; on success it stores the origin-scoped second factor the response body returns (`storeSessionBinding`, `@/lib/session-binding.ts`) BEFORE navigating — `location.replace` tears the page down, so anything still pending never runs — then full-navigates to `/mail` so the next server render sees the fresh cookie. With no token in the hash it falls back to the ordinary `/unlock` screen, which also accepts the old link shape (fragment first, then query) pasted into its box, for a link printed by an older build. `unlock-screen.tsx` is the recovery/paste-box screen at `/unlock` (rendered when the link carries no `?exchange=1`, or `UnlockExchange` found no token in the hash): it deliberately offers NO self-service way to mint a token — only to redeem one already obtained out of band (the printed link, or `npx email-agent unlock`) — because it is reachable by definition with no credential, and a mint control on it would let exactly the parties it exists to keep out unlock themselves. It accepts either a bare token or the whole printed URL pasted in (`extractUnlockToken`, fragment first then query — the only path that still redeems a link from an older build), runs its own `POST /api/auth/unlock` exchange and its own `storeSessionBinding` on success, and renders distinct copy for `invalid-token`/`token-expired`/`token-already-used`/`rate-limited`, plus a `reason === "binding"` variant that explains a live-but-unbound session rather than claiming "locked".
- scope boundaries: Renders, reads the fragment, and POSTs/writes `localStorage` only; the session cookie itself is set by the exchange route's `Set-Cookie`, never read or written here. Says nothing about a second device — the printed link, the cookie and the second factor are all host/origin-scoped, and that is out of scope by design (see the TODOS.md scope note this feature shipped against).
- connected modules/submodules: `modules/api/auth-contract.ts` (core-free error-code wording, kept separate from `@email-agent/core/config` because these are client components and the config barrel pulls `node:fs`/`node:crypto` at module load), `@/lib/session-binding.ts` (writes the second factor `unlock-exchange.tsx` receives), the `/unlock` page (`app/unlock/page.tsx`), the root `app/page.tsx` dispatcher, the `(app)/layout.tsx` gate.
- allowed change types: Unlock/exchange UI copy and layout; the token-extraction/paste-box behavior.
- special operating rules: `unlock-screen.tsx` is rendered by `unlock-screen.test.tsx` (RTL) — every `reason` state's copy (via `describeUnlockScreenCopy`, `modules/api/auth-contract.ts`), the coded-failure and network-error message branches, and the submit-button disabled/enabled wiring; NOT the success path, because `window.location.replace` cannot be redefined in jsdom (measured). `unlock-exchange.tsx` remains rendered by nothing — it hits the same `location.replace`/`.assign` wall on every branch that matters (its success path, and its `noToken` fallback into `UnlockScreen` is the only branch that doesn't navigate, which is already covered via `UnlockScreen`'s own tests) — so it is still verified only by reading and, for the real flow, by `packages/cli/src/commands/serve.browser.e2e.test.ts` driving a real Chromium against a real `email-agent serve`. `unlock-exchange.tsx` must call `history.replaceState` BEFORE the network round trip, not after.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: None known.
- docs that must stay aligned: AGENTS.md's unlock bullet, README's "Unlocking the local UI" section.
- local validation commands/checks: `npx tsc -p packages/web/tsconfig.json --noEmit`; `npm run -w @email-agent/web test -- run unlock-screen` for `unlock-screen.tsx`; `packages/cli/src/commands/serve.browser.e2e.test.ts` for the real flow (skips cleanly with no Chromium installed).
