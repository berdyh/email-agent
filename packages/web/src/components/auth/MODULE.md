# Module Card: Web Auth Components

- purpose: Own the client-side half of the unlock flow — the `#token=…` fragment handoff and the static recovery screen.
- product/module functionality: `unlock-exchange.tsx` mounts when the root `page.tsx` dispatcher sees a `token` query param; it scrubs the token from the URL/history immediately (the token has already done its job by reaching the browser, and there is no reason to leave it visible a moment longer while a fetch is in flight), POSTs it to `POST /api/auth/unlock`, and full-navigates to `/mail` on success so the next server render sees the fresh cookie. `unlock-screen.tsx` is the static `/unlock` page: it deliberately offers NO self-service way to mint a token — only to redeem one already obtained out of band (the printed link, or `npx email-agent unlock`) — because it is reachable by definition with no credential, and a mint control on it would let exactly the parties it exists to keep out unlock themselves. It accepts either a bare token or the whole printed URL pasted in, and renders distinct copy for `invalid-token`/`token-expired`/`token-already-used`/`rate-limited`.
- scope boundaries: Renders and POSTs only; the session cookie itself is set by the exchange route's `Set-Cookie`, never read or written here. Says nothing about a second device — the printed link and the cookie are both host-scoped, and that is out of scope by design (see the TODOS.md scope note this feature shipped against).
- connected modules/submodules: `modules/api/auth-contract.ts` (core-free error-code wording, kept separate from `@email-agent/core/config` because these are client components and the config barrel pulls `node:fs`/`node:crypto` at module load), the root `app/page.tsx` dispatcher, the `(app)/layout.tsx` gate.
- allowed change types: Unlock/exchange UI copy and layout; the token-extraction/paste-box behavior.
- special operating rules: There is NO component testing library in this repo, so both components here are verified by reading and, for the real flow, by `packages/cli/src/commands/serve.browser.e2e.test.ts` driving a real Chromium against a real `email-agent serve` — that file is the only place either component is actually exercised end to end. `unlock-exchange.tsx` must call `history.replaceState` BEFORE the network round trip, not after.
- current stubs/placeholders: None known.
- irrelevant or incomplete code to remove/rework: None known.
- docs that must stay aligned: AGENTS.md's unlock bullet, README's "Unlocking the local UI" section.
- local validation commands/checks: `npx tsc -p packages/web/tsconfig.json --noEmit`; `packages/cli/src/commands/serve.browser.e2e.test.ts` for the real flow (skips cleanly with no Chromium installed).
