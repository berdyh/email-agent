# Module Card: Web API Contracts

- purpose: Own request validation, request guards, and route-local wire contracts for Next API handlers.
- product/module functionality: Parse and validate JSON bodies before route handlers call core modules.
- scope boundaries: Does not own core business behavior or UI state.
- connected modules/submodules: Next API routes under `app/api`, core Gmail/actions/settings modules, `oauth-state.ts` for the OAuth callback flow, `approvals-contract.ts` (shared with `hooks/use-approvals`), `approval-rows.ts` (row → wire shape, shared by the pending and stranded lists), `action-run-contract.ts` (run-result wording, shared with `app/actions`), `retention-contract.ts` (approval-queue retention field parsing and helper text, shared with `app/settings`).
- allowed change types: Request parsers, validation errors, route-adapter-only DTOs.
- special operating rules: State-changing routes must validate input and mutation origin before touching core/file/DB/Gmail modules; `gmail.autoApplyActions` must stay gated on `gmail.autoApplyAcknowledged` in both `mergeSettingsUpdate` and `sanitizeSettingsForResponse` (see `normalizeGmailConfig`), so a client cannot enable unattended Gmail writes by sending the toggle alone — enforced TWICE (here and in core's `normalizeSettings`) on purpose, but implemented ONCE: `normalizeGmailConfig` is a call to core's `normalizeAutoApplyConsent`, not a copy of it, because two copies of a consent rule drift in the direction of honouring the toggle without the acknowledgement; non-local or cross-site browser writes require `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1`, and mutations must additionally carry `Origin` or `Sec-Fetch-Site` (browsers always do; a bare `curl` does not) — but treat all of it as anti-CSRF/anti-rebinding hardening, NOT a boundary, since every input is a caller-controlled header; the boundary is the loopback bind in `packages/web/package.json` and `cli/commands/serve.ts`. EVERY handler under `app/api` must call `mutationGuardResponse` or `readGuardResponse` — `route-guards.test.ts` walks the tree and fails otherwise; the sole exemption is `GET /api/auth/callback` (top-level cross-site redirect from Google, protected by its one-time state cookie), and it is named in that test. `readGuardResponse` deliberately does not require the fetch metadata so the address bar still works. The guards read the `Host` HEADER, never `request.url`: installed Next composes that URL from the server's own configured hostname, so it neither carries the caller's host nor matches the origin the browser is using. `approvals-contract.ts`, `action-run-contract.ts` and `retention-contract.ts` must stay free of `@email-agent/core` imports — client hooks and pages import them, and web code outside this module may not pull core runtime into the browser bundle. That is why `describeActionRunOutcome` PRINTS the failure strings core already composed (`applyError`, `queueError`) rather than rebuilding them. `sanitizeSettingsForResponse` must keep returning `retention`: it was omitted, so the Settings page could not show that resolved audit rows are deleted on a schedule the user never chose — and it is now the page's ONLY source for the default window, so no client-side literal can drift from `defaultConfig`. `snapshot-contract.ts` owns the action-snapshot wording, and the rule it exists for is that a restore REFUSED by the source guard must reach the user as the specific rules it broke — `POST /api/actions/user/snapshots` answers 422 with `UnsafeActionSourceError.violations` rather than a 500, because a snapshot that predates the guard is not a server error and a generic failure leaves a user with an unrecoverable action and nothing to act on (the CLI has always printed the rules). `retention-contract.ts` owns the field's parsing and its three helper sentences; an empty input is `null`, never `0`, because `Number("")` is 0 and 0 means "keep every record forever" here. A shortfall reported by `POST /api/approvals/stranded` means "not written by this call" and now has FOUR possible causes — an apply resolved the row, another PERSON answered it (another tab, or the CLI), Email Agent's own automatic Gmail check answered it in the meantime, or it was requeued and re-claimed inside the staleness threshold; `describeStrandedResolution`/`strandedSkipReasons` offer all four and assert none, the same rule `unclaimedApplyMessage` follows. The automatic-verification cause is stated SEPARATELY from "another person answered it" — a user who pressed nothing themselves cannot guess the first exists, so folding it into "another answer" would read as impossible to them. A new mutation-guarded route, `POST /api/approvals/stranded/verify`, calls core's `verifyStrandedApplyingOperations()` and returns `{checked, appliedRecorded, requeuedRecorded, unresolved: [{id, emailId, accountId, reason, detail}]}` — `reason` is one of FIVE (`message-missing`, `credentials`, `check-failed`, `unverifiable-operation`, `unscoped-account`), duplicated core-free as `VerificationResidualReason` in `approvals-contract.ts` the same way `StrandedDecision` already is. It is a MUTATION, not a read, deliberately: it calls Gmail and writes rows, so `GET /api/approvals/stranded` stays a pure DB read behind `readGuardResponse` and this sits behind `mutationGuardResponse` instead. It is fired ON-DEMAND (once per panel mount, ref-guarded — never on a background refetch, which would turn a one-time check into a polling loop) rather than on the automatic `serve`-startup/`fetch` cadence those two CLI commands use; both paths reach the same core primitive, which is gated on a cheap DB read and makes zero Gmail calls when nothing is stale. `describeVerifyResolution`/`describeResidualReason` (`approvals-contract.ts`) are the pure wording for what a verify pass found and why a residual row is still residual — `unverifiable-operation` is worded as something that will NEVER resolve itself, `check-failed` as something that MAY. Both approval lists build their rows through `toApprovalOperations` so the label a user reads before deciding a message's fate cannot differ between the pending and the stranded list. The batched email lookup is core's `getEmailsByIds` (`@email-agent/core/db`), not a local helper — it was duplicated here and in the CLI and both copies went wrong together twice; email-id request bodies and detail queries must include `accountId`, and an explicitly empty value is valid for legacy/gcloud ADC rows; legacy settings written under a removed shape (e.g. old `notifications`, `oauth`, `ui.theme`, `ui.sidebarCollapsed`, `prompts.priority`, `prompts.clustering` keys) must be normalized/dropped before route handlers persist an update, not passed through; `oauth` held a Google OAuth client secret that nothing ever read (`getOAuthCredentials()` reads only `~/.email-agent/oauth.json`) — `PUT /api/settings` now refuses it with `Unknown setting: oauth` (400) rather than accepting and round-tripping it, and `settings.route.test.ts` proves a settings.json seeded with a pre-removal `oauth` block has it purged on the next save; `oauth-state.ts` owns the OAuth CSRF-state cookie — `generateOAuthState`/`setOAuthStateCookie` on auth-url issuance, `isValidOAuthState` (timing-safe compare, length-checked FIRST because `timingSafeEqual` throws on unequal lengths) on callback, and the redirect URI is derived from the request origin (not hardcoded) so `serve --port N` keeps working; it is exercised by `oauth-csrf.route.test.ts` through both real handlers, but has still never run against a live Google consent flow. `groupOperationsByBatch` (`approvals-contract.ts`) is the approval panel's batch grouping, out here because what it holds is ORDER: the route returns rows already sorted, a Map preserves insertion order, and grouping with an object literal or sorting the keys throws that ordering away and can repeat a batch header.
- test harness: `testing/route-harness.ts` drives REAL route handlers against a real temp-`$HOME` LanceDB. There is no HTTP, no server and no mocking layer — a handler is a plain async function, and the only thing that ever blocked this was that tsx does not resolve the `@/*` and `@email-agent/core/*` tsconfig `paths`, which `testing/module-aliases.mjs` fixes with a `module.register()` resolve hook mirroring exactly those two alias entries. Keep the hook and the tsconfig in step: a divergence means a route resolves differently under test than in the app. The database half is core's `useTempHome()`, imported through the alias so the test and the route share ONE core module instance. It covers handlers, NOT Next (routing, middleware, streaming, server-component rendering) and NOT React — there is no component testing library in this repo, so no panel is rendered by any test.
- malformed JSON bodies: `parseJsonBody(request)` (`validation.ts`) is the ONE place any route parses a request body now — every mutating route calls it instead of `request.json()` directly. It catches only `SyntaxError` and rethrows as `RequestValidationError("Request body must be valid JSON")`, which `validationResponse` maps to 400; anything else `.json()` throws (a body already consumed, a stream error) is rethrown unchanged as a real 500. Deliberately narrow — catching every `SyntaxError` a route's try block might raise would misclassify one thrown somewhere else in that block as a bad client body. `approvals.route.test.ts`'s malformed-body assertion was flipped from 500 to 400 in the same commit that added `parseJsonBody`.
- current stubs/placeholders: None known; local parsers are intentionally dependency-free to avoid package/lockfile churn.
- irrelevant or incomplete code to remove/rework: None known.
- docs that must stay aligned: Route handlers, module index, README environment variables, API smoke checklist.
- local validation commands/checks: `npm test -- packages/web/src/modules/api/*.test.ts`, `npx tsc -p packages/web/tsconfig.json --noEmit`.
