# Email Agent

Local AI-powered email analysis tool. Monorepo with Turbo.

> **Worktree:** This directory is a git worktree; the bare repo is at `../.bare/`, which carries the
> project-level memory files. See the global agent instructions for git worktree SOPs.
>
> **`CLAUDE.md` and `AGENTS.md` are ONE FILE.** `CLAUDE.md` is a symlink to `AGENTS.md`, so every
> coding agent reads the same bytes and there is nothing to keep in sync. They used to be two
> separate files with overlapping content, and they drifted: a stale `mergeInsert` recommendation
> survived in one after being disproved in the other, `getEmails` was still described as chaining
> `.where()` months after it stopped, and a find/replace had turned the whole Agent Executors
> section into advice about a `Codex-executor.ts` and a `Codex` env var that do not exist. Every
> agent session loads one of these files, so a wrong line in the copy you did not fix teaches the
> wrong thing until someone notices. `scripts/check-module-boundaries.mjs` fails if the symlink is
> ever replaced by a regular file (a Windows checkout, or an editor that breaks the link).

## Commands

```bash
npm install              # Install all dependencies
npm run build            # Build all packages (core must build first)
npm test                 # Run Node test suite through tsx (builds core AND cli first — the CLI e2e tests run the built binary)
npm run check:boundaries # Verify module cards and import boundaries
npm run dev              # Start all dev servers
npm run start            # Start web UI on port 3847
npm run setup            # Interactive setup wizard (gcloud auth + DB init)
npx tsc -p packages/core/tsconfig.json --noEmit   # Type-check core
npx tsc -p packages/web/tsconfig.json --noEmit    # Type-check web
npx tsc -p packages/cli/tsconfig.json --noEmit    # Type-check CLI
```

### CLI

```bash
npx email-agent fetch              # Fetch unread emails → LanceDB (--scope all|unread, --limit N)
npx email-agent fetch --account <email>  # Fetch for a specific account
npx email-agent accounts list      # List configured Gmail accounts
npx email-agent accounts add <email>     # Add account via OAuth2
npx email-agent accounts remove <email>  # Remove account
npx email-agent accounts default <email> # Set default account
npx email-agent run-action <id>    # Run an action (priority, subscription, junk)
npx email-agent list-actions       # List available actions
npx email-agent actions snapshots  # List saved versions of user actions (--action <file>)
npx email-agent actions snapshots restore <snapshot>  # Restore a snapshot (--action <file>, -y)
npx email-agent approvals          # List Gmail changes queued for approval
npx email-agent approvals review   # Approve/reject each queued change interactively (--batch <id>)
npx email-agent approvals apply    # Approve and apply queued changes in bulk (--batch <id>)
npx email-agent approvals reject   # Reject queued changes without applying (--batch <id>)
npx email-agent approvals stranded # Checks Gmail first, resolves what it can; --review adjudicates what's left
npx email-agent approvals prune    # Delete resolved queue rows past the retention window (--older-than-days N, --dry-run)
npx email-agent setup              # Authenticate + configure project + init DB (--project <id>)
npx email-agent serve              # Start web UI (--port <port>, default 3847; --host; binds loopback unless --host/EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1; prints a one-time unlock link before spawning the server)
npx email-agent unlock             # Print a fresh one-time link that unlocks the web UI in a browser (--port, --host); needs no running server and works on one already up
npx email-agent cron setup         # Install crontab for periodic fetching (--interval, --scope, --limit)
npx email-agent cron status        # Show current crontab entry
npx email-agent cron remove        # Remove crontab entry
npx email-agent config get <key>   # Read config value (dotted path, e.g. ui.fetchScope)
npx email-agent config set <key> <value>  # Set config value
```

## Architecture


For module/submodule work, load `docs/architecture/module-index.md` first, then the local `MODULE.md` card beside the area being changed.

## Key Patterns

- **Multi-account Gmail**: OAuth2 per-account auth in `gmail/account-manager.ts`, tokens at `~/.email-agent/accounts/{email}/token.json`, OAuth creds at `~/.email-agent/oauth.json`. `client.ts` routing: explicit account → default account → gcloud ADC fallback. `accountEmail?: string` threaded through all Gmail operations. Account removal/default-change calls `resetGmailClient()` to invalidate cached clients.
- **Email identity**: Treat Gmail message ids as account-scoped. DB upserts, read-state updates, detail routes, Gmail write operations, and selected-mail UI state must carry `accountId` with `id`; empty `accountId` is the legacy/gcloud ADC account sentinel and is valid when explicitly present.
- **Unread sync reconciliation**: Complete unread-scoped syncs should mark same-account local unread rows as read when Gmail no longer returns them; do not use whole-table overwrite to clear stale unread rows.
- **Agent system**: Strategy pattern executors (Claude SDK/CLI + Codex/Gemini CLI + DirectAPI + OpenRouter) with AgentRouter; supports streaming via `executeStream()`
- **Action system**: Plugin architecture — `*.action.ts` files auto-discovered from built-in + user dirs. Discovery is not execution: built-ins are real `import()`s (in-repo, reviewed); user files in `~/.email-agent/actions/` are PARSED as pure data and never enter the module graph
- **Approval gate**: Action runs never mutate Gmail directly. `ActionRunner` maps results to Gmail operations and always enqueues them in the LanceDB `pending_operations` table first (`actions/approval.ts`, batchId = action_results row id), so every proposed change is recorded before anything touches Gmail. Mutations then happen via `applyPendingOperationsByIds()` after explicit user approval: web `ApprovalPanel` on `/actions` (per-email checkboxes + review dialog, `/api/approvals*` routes) or CLI (`run-action` prompt, `approvals` command). Rejected/applied rows are kept as an audit trail. Both surfaces distinguish "this run claimed nothing" from a no-op: core claims each row before touching Gmail, so `requested - (applied + failed)` is exactly the set of ids THIS CALL DID NOT CLAIM — `POST /api/approvals/apply` reports it as `skipped` (the CLI calls it `unclaimed`) and answers 409 when nothing at all was claimed, instead of "Applied 0 changes". **Read that number as "not claimed here", never as "already applied or rejected":** a row this call could not claim may be `applying` in a request that is still running, may have failed earlier, or may not exist. The messages on both surfaces offer those as possibilities and assert only that this run did not touch the row. `requested`/`skipped` appear on the 200 and the 409 — the two responses the apply itself produces; a guard failure (403), a validation failure (400) and an unexpected error (500) return `{ error }` only. Manual per-email actions the user clicks in the mail UI stay immediate — the click is the approval. **User action files are never executed**: `loadUserAction()` and `ActionRegistry`'s `ACTIONS_DIR` pass read each `*.action.ts` and statically evaluate it with `extractActionData()` (`actions/action-source-guard.ts`), which returns the action object without the file entering the module graph. Built-ins stay real `import()`s — they are in-repo and reviewed. This is what makes the save-time guard unnecessary *for safety*: a file that was hand-dropped, or written before the guard existed, cannot run either. Behaviour change to know about: a hand-**written** action that computes anything (concatenation, a value import, a function call) no longer loads at all, and is refused loudly with its violations in a `console.warn` — such a file could never have been saved through the app, so the only people affected are power users hand-authoring executable actions, which the threat model does not want. The mutating surface is **barrel-private**: `applyOperations`, the raw Gmail write ops, and the client factories (`createGmailClient`/`createGmailClientForAccount` — every write op is a one-line wrapper over them) are not exported from any public barrel, and the `exports` map exposes no subpath to `gmail/operations` or `actions/apply`, so the one-line `import { applyOperations } from "@email-agent/core"` bypass is closed (pinned by `packages/core/src/barrel-surface.test.ts`, which also checks the dist surface and pins the `exports`-map keys — keep it passing when touching barrels). Scope it honestly: this is defense in depth against a *naive* import (the realistic failure, since actions are LLM-written), not an enforcement boundary — and now that `ACTIONS_DIR` files do not execute, it is no longer load-bearing for user actions at all. What has NOT changed: any other local code runs in-process with full Node privileges, so a hostile *program* on this machine never needs core — it can read the stored OAuth tokens at `~/.email-agent/accounts/{email}/token.json` and call the Gmail REST API directly. The improvement is narrow and worth stating precisely: a file sitting in `ACTIONS_DIR` is no longer such a program. Even staying inside core, `new URL("./gmail/operations.js", import.meta.resolve("@email-agent/core"))` is built entirely from public specifiers and returns every raw mutator — the `exports` map blocks the subpath-key form, not the resolve-root-then-relative-URL form. Note also that from the real `ACTIONS_DIR` (`~/.email-agent/actions`) NO bare specifier resolves at all, not even `googleapis`; the barrel privacy therefore bites in workspace-resolvable contexts (web bundling, any future in-tree action loading), and makes a by-name mutation import fail loudly everywhere. Both skill docs prohibit actions from importing anything but `type { EmailAction }`. The queue's own operational rules: the `action_results` row is written **before** its queue rows (they carry `batchId = resultId`, so the reverse order can orphan them; if the parent write fails, nothing is queued); an enqueue makes a **best-effort** skip of proposals identical to a row already **pending** (a re-proposal after a rejection or an apply is legitimate and is NOT suppressed) — it is a check-then-insert, so two concurrent runs can both read before either writes and both insert, producing duplicate rows for the same change; do not document it as a uniqueness guarantee. How bad that is depends on auto-apply: with the gate on the duplicates sit in the pending list and the user can reject one, but with `gmail.autoApplyActions` on each racing runner immediately applies its own ids, so neither is ever pending for review and **Gmail receives both calls**; `applyPendingOperationsByIds()` **claims**, applies and resolves in chunks of 10 with the claim inside the loop, so the claimed set and the in-flight set coincide: a crash or DB failure strands at most one chunk in `applying`, and every later id is still `pending` and still approvable/rejectable (claiming the whole batch up front bounded only the mutated-but-unrecorded set). **That bound is PER CALL, not per batch** — nothing serializes two concurrent applies over one batch, and they leapfrog (A claims ids 1-10 and calls Gmail; B loses those, continues, and claims 11-20 while A is in flight), so a crash strands one chunk per in-flight caller; never restate it as a per-batch guarantee; rows a crash left in `applying` can be listed by `getStaleApplyingOperations()` (age measured from `claimedAt`) rather than retried — `verifyStrandedApplyingOperations()` now checks most of them against Gmail itself before a user ever would (see the bullet below); the rest still need a person; and `prunePendingOperations()` deletes `applied`/`rejected` rows past `retention.approvalQueueDays` (default 365, non-positive disables) after every apply/reject — never `pending`, `applying` or `failed`. `ActionRunResult` distinguishes `queueError` (strictly pre-Gmail: nothing was applied) from `applyError` (auto-apply threw after the rows were claimed, so Gmail **may** already have been mutated) and `persistError`; never report the second as the first. **`approvedVia`** (`"web"` | `"cli"` | `"auto-apply"` | `""`) records which surface claimed a row, written by `claimPendingOperations()` — the single place a row leaves `pending` — as a required parameter with no default. It is **attribution only: it gates nothing and proves nothing**, and must never be read as a security control — there is no unforgeable in-process caller identity to derive it from (ESM module identity is process-global), so it is exactly as trustworthy as the caller that set it. `""` means unclaimed-or-legacy and must never be backfilled or guessed onto an existing row, including at migration (the sentinel is `CAST('' AS STRING)`). `adjudicateStrandedOperations` clears it back to `""` only on a `notApplied` answer (the row is genuinely unclaimed again); an `applied` answer deliberately leaves it, so a stranded row keeps recording which surface initiated the crashed apply.
- **Applying approved operations is serial, and stays that way for now.** `applyOperations()` awaits one Gmail round trip per operation and returns exactly one outcome per input operation IN ORDER, because `toOperationOutcomes` pairs them positionally with the claimed rows. `messages.batchModify` is REJECTED rather than pending, on two grounds read off its REST reference (2026-08-07): its success response body is empty, so it reports no per-message result (N rows would collapse onto one all-or-nothing status — the ambiguity that mapping deliberately fails closed on), and one request is one `ids[]` list against one `addLabelIds`/`removeLabelIds` pair under one `userId`, so only identical (account, addLabelIds, removeLabelIds) tuples could share a call — a junk batch (trash + spam + archive interleaved) is three distinct tuples and fragments into single-operation calls anyway. It is NOT rejected for being unable to express `trash`; an earlier revision of this bullet asserted that and it was false. `TRASH` is a manually-appliable system label (unlike `SENT`/`DRAFT`) and `batchModify` restricts `addLabelIds` only by the 1000-id cap, so `addLabelIds: ["TRASH"]` is the batched equivalent of `messages.trash()` — the same relationship `markAsSpam()` already relies on with `modify` + `["SPAM"]`. `batchDelete` is the analogue of `messages.delete` (PERMANENT) and must never be substituted for trash, but that is not a ground against `batchModify`. A bounded pool is deferred: it would have to partition by (account, message) and stay serial inside a partition (several pending operations can target one message, and serial order is the order the user reviewed), it must wait for retry/backoff (a failure here is TERMINAL — a `failed` row is not `pending`, so an approved change is dropped until the action is re-run), and it must live strictly INSIDE one chunk, since spanning chunks would put two chunks in flight and undo the reason the claim sits in the loop.
- **A queued row's `accountId: ""` is resolved at APPROVAL time, not at queue time — and now at VERIFICATION time too, a third moment ADC can have moved.** It reaches `createGmailClient("")`, which means gcloud ADC and never a configured default account, so if ADC has been re-pointed since the message was read the row addresses a different mailbox. On the APPLY path this is harmless: Gmail message ids are per-mailbox, so the call 404s and the row resolves `failed` (terminal — the approved change is dropped) rather than mutating the wrong mail. That is a property of Gmail's id space, NOT a guard we implement — do not upgrade it to "cannot mutate the wrong mailbox". `verifyStrandedApplyingOperations()`'s Gmail READ-BACK is not symmetric: a wrong-mailbox 404 costs nothing (it becomes a `message-missing` residual), but a wrong-mailbox message that happens to carry the same id and already-matching labels would return a positive verdict — so a `""` row may be READ and, if it fails to match, REQUEUED to `pending` (an ordinary proposal needing approval again, which costs nothing), but it may never be recorded `applied` on that evidence; it is left for a human instead (`unscoped-account` residual). Named-account rows are unaffected by any of this.
- **What the approval queue's records now reach the user as, and what they still do not.** Every field `ActionRunner` writes is read by both surfaces. `applyError` (auto-apply threw AFTER the rows were claimed and Gmail may already have been mutated) is printed VERBATIM from core's `describeAutoApplyFailure` by `describeActionRunOutcome` (`packages/web/src/modules/api/action-run-contract.ts`) and `describeRunOutcome` (`packages/cli/src/commands/run-action.ts`); on that branch neither surface reports the batch as awaiting approval and the CLI does not prompt to apply anything, because those rows are `applying`, not `pending` — reporting them as pending, and offering the leftovers of a multi-chunk abort, was the shipped bug. `persistError` and `duplicateOperations` are surfaced too, the latter so a queue that grows by fewer rows than the action proposed explains itself. `getStaleApplyingOperations()` is called by `GET /api/approvals/stranded` (rendered by `StrandedOperationsPanel` above the approval panel) and `email-agent approvals stranded [--review]`; `approvals list` points at it as well, since those rows are invisible to every `pending`-scoped command. Adjudication goes through `adjudicateStrandedOperations(ids, "applied" | "notApplied", { evidence? })`. It claims by token AND re-asserts the staleness cutoff inside the same atomic write predicate (`buildStrandedClaimFilter(ids, cutoffIso)`), so neither an apply that has already recorded a real outcome nor one merely in flight inside the threshold can be overwritten — the surfaces filtered their LISTS by age, but the ids they submit are just ids, and a JS pre-filter would leave a window between the age test and the destructive token stamp.

  **A verification pass now runs BEFORE any of this reaches a human**, automatically, at `email-agent fetch` and at `email-agent serve` startup (owner's decision, cadence D1): `verifyStrandedApplyingOperations()` (`actions/verify-stranded.ts`) reads `getStaleApplyingOperations()` FIRST as a cheap DB-only gate — zero rows stale means zero Gmail calls and zero printed output, which is what lets it run unprompted on every `fetch`/`serve` without a daemon, a poll, or the deleted notifications module coming back. `serve` is a genuinely new cost here: it previously had no `@email-agent/core` dependency at all and now opens the database and runs this gate before spawning the Next.js child; `fetch` reuses the connection `syncEmails()` already opens. Both wrap the call in its own try/catch and print one honest line on failure — a verification failure must never break a fetch or a server start that otherwise succeeded. `POST /api/approvals/stranded/verify` (mutation-guarded, not read-guarded — it calls Gmail and writes) is the same check fired on demand, once per `StrandedOperationsPanel` mount (ref-guarded against a background refetch re-firing it); `GET /api/approvals/stranded` stays a pure DB read. `email-agent approvals stranded [--review]` runs the check inline first too, same shape as `fetch`/`serve`.

  For each stale row it reads the message's CURRENT labels (`gmail/read.ts`'s `readMessageLabels`, `users.messages.get` with `format: "minimal"` — barrel-private for a DIFFERENT reason than the write ops in `operations.ts`: it cannot mutate anything, but it hands back mailbox content by message id, so it is deliberately excluded from `barrel-surface.test.ts`'s `deniedNames` rather than added alongside the writers) and compares them to the operation's intended end state via `verdictFromLabels` — `spam` needs SPAM present AND INBOX ABSENT (`markAsSpam` is one atomic `modify` carrying both, so that pair IS the intended end state; a predicate table once drafted for this said "SPAM present" alone and was wrong), `trash` needs TRASH present ALONE (Gmail drops INBOX implicitly on trash; requiring it would manufacture false negatives). It FAILS CLOSED to the human path, never to a verdict, for: an `addLabels`/`removeLabels` row with an EMPTY label list (`applyOperations` throws for those, so such a row could never have been applied by this app); an unrecognised `type`; a 404 (THREE-WAY AMBIGUOUS — permanently deleted, an ADC row now pointing at a different mailbox, or a trash/spam that WORKED and was later purged, so a 404 can mean APPLIED and is never auto-anything); a credentials failure (Gmail's 403 covers both permission and rate-limiting in the same status code, and `gmail/read.ts` classifies on `err.status`, NOT `err.code` — measured against the installed gaxios 6.7.1, re-measure on any googleapis upgrade); and any error from the check itself. A residual row carries WHICH of six reasons it hit (`message-missing`, `credentials`, `check-failed`, `unverifiable-operation`, `unscoped-account`, `not-checked`) — a person told only "we could not check" cannot act, and `unverifiable-operation` in particular will never resolve itself the way `check-failed` might on a later pass. **It reads in TWO passes, and the second covers the requeue candidates ONLY** — see limit 3 below for why that direction and no other. Both passes share one `classifyRow` (a second copy would be a second predicate table, and a drifting one is a bypass) and one `recordApplied` (which owns the `accountId: ""` refusal for every route to an `applied` write). The reads stay serial in both passes, so a row headed for a requeue costs 40 quota units rather than 20.

  **BOTH THE READ AND THE PASS ARE BOUNDED IN TIME, and neither bound is optional.** Until 2026-08-22 nothing under `users.messages.get` supplied a timeout, so a peer that ACCEPTED the connection and never answered — a captive portal, a half-up VPN — stalled the serial loop indefinitely, and with it `fetch`, `serve` (which runs the pass BEFORE spawning the web server) and `POST /api/approvals/stranded/verify`. **The surrounding try/catch is no defence: it catches throws, not hangs.** `MessageLabelRead` had declared an `error` kind naming "timeout" since it was written and nothing could produce one. Three numbers, strictly ordered: `GMAIL_REQUEST_TIMEOUT_MS` (8s, one HTTP request, aborts the socket) < `GMAIL_READ_DEADLINE_MS` (10s, the whole read, applied by `readMessageLabels` OUTSIDE the getter's credential catch so a deadline is never reported as "your Google access is broken") < `STRANDED_VERIFICATION_DEADLINE_MS` (20s, the whole pass). **The worst case is `pass budget + one read deadline` = 30s, not 20s** — the budget is checked BEFORE each read and the read that starts just inside it runs to its own bound; never quote 20s as the ceiling. MEASURED against the installed googleapis 146.0.0 / gaxios 6.7.1 / node-fetch 2.7.0 (2026-08-22) by pointing a real client at a `node:http` server that accepts and never responds, NOT read off documentation: (1) `timeout` is declared in gaxios's `common.d.ts:104` and NEVER READ anywhere in `gaxios.js` — it works only because `common.js:66` picks node-fetch when there is no `window` and hands it the options verbatim, so **gaxios 7, which drops node-fetch for the platform `fetch`, would keep the option compiling and silently remove the bound**; re-measure on any googleapis/gaxios upgrade, exactly as for the LanceDB facts; (2) without it the call was still pending at 4,000ms; (3) `retryConfig: { noResponseRetries: 0 }` is REQUIRED for the number to mean what it says — `googleapis-common/apirequest.js:263` defaults `retry: true` and gaxios retries a no-response failure twice more, so bare `timeout: 800` measured 3,013ms and `timeout: 1500` measured 5,115ms, against 802ms/301ms with the override; it suppresses ONLY no-response retries, so 429 and 5xx (which are responses) keep theirs, which matters because these reads are serial precisely to stay clear of 429s; (4) the rejection is a `GaxiosError` with `name: "Error"`, NO `status` and `err.error.type === "request-timeout"`, so `classifyMessageReadFailure` maps it to `error` -> `check-failed` with no special case. The pass budget is checked before every read in BOTH passes and is skipped for the FIRST row of pass one — a budget that could refuse the first row would make the pass a permanent no-op and the queue would never drain. A requeue candidate the budget stopped short of RE-READING becomes a `not-checked` residual and is **NEVER requeued on pass one's evidence**, which is exactly what the re-read exists to distrust. Both adjudication writes still run for whatever the pass DID decide: the budget bounds the Gmail reads, not the local database writes. The chosen shape is a deadline in CORE rather than re-ordering `serve` to spawn its Next child first, because every caller inherits the core bound while re-ordering fixes one command and leaves the fetch tail and the route POST exposed (and would need the child moved off `stdio: "inherit"` onto pipes). D1's cheap-gate property is untouched: nothing stranded still means zero Gmail calls, zero output and no clock read at all.

  **`resolutionEvidence`** (`"user-confirmed"` | `"verified-api"` | `""`, a new `pending_operations` column, same sentinel discipline as `approvedVia`) records HOW a stranded row's resolution was established — a resolve-time question, separate from `approvedVia`'s claim-time one. `adjudicateStrandedOperations` is the SINGLE write path for both sources, not two functions: the automatic verifier calls it with `evidence: "verified-api"` for what it resolved itself, stamping `STRANDED_VERIFIED_NOTE` (a sibling of `STRANDED_APPLIED_NOTE` that says plainly it is an end-state match, not proof of causation); the two human surfaces call it with the default `"user-confirmed"`, stamping `STRANDED_APPLIED_NOTE`, only for the residual the verifier could not answer. `""` deliberately means three things at once — unresolved, resolved by its own healthy apply, or written before the column existed — and must never be rendered as "verified" or guessed onto a migrated row.

  **No row with `accountId: ""` (the ADC sentinel) may ever be recorded `applied` by this pass** — see the ADC bullet above for why; it may only be requeued to `pending` (`unscoped-account` residual) or left for a human.

  **Do not describe either path as recovery.** Both record an end state or hand the row to a person; neither re-applies anything nor rolls anything back. **THREE limits, not fewer, survive from the design and cannot be engineered away:**
  1. It reads the state NOW and cannot prove THIS APP'S CALL caused it — no check, automated or human, distinguishes "we did this" from "it was already like that" (unchanged from before this pass existed). A message archived by hand five minutes earlier is credited to the app; end state right, attribution wrong, and this direction is benign — the row simply retires.
  2. **The MIRROR, and the dangerous direction:** an apply that really landed and was then UNDONE by the user (un-archived, re-marked unread, restored from Trash) verifies `notApplied` and is RE-PROPOSED as an ordinary pending row needing an explicit approval — but this is the direction that can produce a SECOND mutation if approved again, undoing the user's own later action. The whole operation set is idempotent label state (no send, no permanent delete, no counter — `gmail/operations.ts` has no `messages.delete`/`batchDelete`), so the honest sentence is: idempotent, therefore it cannot destroy anything; it can still undo something the user did in between.
  3. The read-before-write window is NARROWED, NEVER CLOSED, and only one direction of it was ever a defect. A hung apply landing between this pass's read and its write falsifies a `notApplied` (the change is then BOTH in Gmail and back in the queue, on an audit trail saying it never happened, and a later approval can send it again); it cannot falsify an `applied`, because labels the check SAW present were present, so a late apply agrees with the record. So every requeue candidate — and ONLY those, since re-reading the applied set buys nothing and spends quota — is RE-READ immediately before adjudication, collapsing the exposure from the whole serial read pass plus both batch writes (seconds to minutes: the reads are serial for 429 reasons, so row 1's evidence is already minutes old when its claim lands) down to one read and one write. **The remainder is irreducible: Gmail can still land between the re-read and the write** — an external system and a local database cannot be read and written atomically — so write "narrowed", never "closed". A candidate that FLIPS to `applied` on the re-read is a SECOND route to an `applied` write and goes through the SAME `recordApplied` the first pass uses, so the `accountId: ""` refusal covers both (a duplicated check is how the new route would silently lose it; mutation-checked — deleting the guard fails all four ADC tests, unit and real-table). A re-read that FAILS never falls back to the first read: no verdict on evidence that could not be refreshed, so the row stays `applying` for a human. And none of this can be fixed by claiming before reading: a crash between claim and release would re-stamp `claimedAt` and hide the row for another threshold, which is strictly worse.

  **State the window that REMAINS, not the half that is covered — narrowed, not removed:** an apply hung PAST the threshold which then returns from Gmail still loses, exactly as before this pass existed. Verification narrows WHICH rows reach that window (only the ones neither the API check nor a person has yet closed); it does NOT close the window itself — `verify-stranded.test.ts`'s own barrel-entry/window tests pin that fact directly rather than leaving it assumed. Its write-back is scoped to the claim token the adjudication overwrote, so it matches zero rows; `resolveClaimedOperations` reads back by token, warns and names the rows, but nothing prevents it — and after a "it didn't happen" answer, from either source, the row is `pending` again, so the same change can reach Gmail a SECOND time behind an audit trail saying it never happened. That losing direction is deliberate: letting the hung apply win would leave a resolution unable to close out a row it has genuinely checked, which is the failure this surface exists to remove. The count returned is a read taken AFTER the write, not the post-claim read (which over-reported under two concurrent adjudications, crediting one for rows the other's opposite answer decided); it can UNDERCOUNT — a requeued row a fresh apply claims before the count read — but never overcount. Every surface therefore gives a shortfall's cause as one of FOUR possibilities, not three: an apply finished it; another PERSON already answered it (another tab, or the CLI/web UI); Email Agent's own automatic verification pass may have answered it in the meantime; or it was requeued and re-claimed and is too new to adjudicate — the third is offered SEPARATELY from the second, because a user who pressed nothing themselves cannot guess an automatic check exists.

  **A requeued row is an ordinary pending row, and auto-apply cannot special-case it (owner's decision D3 — checked against the code, not assumed).** `ActionRunner`'s auto-apply path applies only the ids `enqueueOperationsDetailed()` just inserted; that function makes a best-effort skip of proposals identical to a row already `pending` (`getPendingOperationsForEmails`'s predicate is `status = 'pending' AND emailId IN (…)`), so a re-run proposing the identical change is deduped away and never enters the auto-applied set — in practice a requeued row sits in `pending` until a human or the next verification pass resolves it, not because of a special-case guard but because the existing dedupe already has this effect. Caveat, pre-existing and unchanged by this pass: the dedupe is check-then-insert, so two CONCURRENT runs can each insert a fresh duplicate before either sees the other's row, and with `gmail.autoApplyActions` on, one of those new rows can be auto-applied — the requeued row itself still needs an explicit approval regardless.

It is an **allowlist over the TypeScript AST**, not a denylist over text: a file may contain only type-only imports/exports, type declarations, variable statements whose initializers are static data, and `export default`. Also refused: an ambient `declare` (binds nothing, so the name leaks the real global), `using` (its disposal hook is a call the file never spells), and `__proto__` as an object-literal key (sets a prototype rather than binding a property) — the recurring lesson is to ask "does this syntax BIND what it appears to bind at runtime?", not "is this syntax inert?". So: a named export is read as a LIVE binding at the end of the walk (`export var action = {…}; var action = null` yields nothing, as `mod.action === null` does) while `export default` snapshots its operand where it stands; `mod.default ?? mod.action` coalesces on the VALUE, so `export default null` still falls back to a named `action`; and files the runtime would reject with `SyntaxError` are refused rather than evaluated, because `parseDiagnostics` is a syntax pass only and misses the strict-mode early errors — `reserved-binding` (`eval`, `arguments`, `await` and the nine strict-mode reserved words), `duplicate-declaration`, `duplicate-export`. Where semantics cannot be matched, the rule is to refuse, never to guess. ### Database
- LanceDB `createEmptyTable()` requires Apache Arrow `Schema`/`Field` objects, NOT plain JS objects
- DB record interfaces need `[key: string]: unknown` index signatures for `table.add()`
- **LanceDB HAS schema evolution. Never drop and recreate a table to add a column.** `@lancedb/lancedb` **0.15.0** exposes `Table.addColumns([{ name, valueSql }])`, `alterColumns` and `dropColumns`. Verified 2026-08-07 against the installed native binary (`lance` 0.22.0) on a real table, not from docs: `addColumns` adds the column **in place**, every row survives with its values, and the column is immediately `update()`-able and `where()`-filterable (backticked). The resulting Arrow type is exactly what the CAST names — `CAST('' AS STRING)` → Utf8, `CAST(0 AS INT)` → Int32, `CAST(false AS BOOLEAN)` → Bool — each with the same nullability a fresh `createEmptyTable` of that schema produces. Two caveats: columns are APPENDED, so a migrated table's column order differs from a fresh one (nothing resolves columns positionally, but do not assert order equality); and a `FixedSizeList` vector column cannot be produced this way. **These are facts about a version** — re-verify every one of them if you upgrade `@lancedb/lancedb`
- Adding a column to any table: add the field to that table's Arrow schema in `db/connection.ts` and an SQL sentinel to its `*ColumnDefaults` map. `migrateSchema()` probes with `missingColumns()` and calls `ensureTableColumns()` (`db/migrations.ts`), which adds it in place. The sentinel must produce EXACTLY what a fresh insert writes, so a migrated row is indistinguishable from one written today — for `pending_operations` that means a queued row comes back queued and unclaimed, never silently approved. A missing column with no declared sentinel THROWS rather than being filled with NULL
- **Do not re-introduce read → drop → create → re-insert.** It was adopted from a comment asserting "LanceDB has no ALTER TABLE" that was simply false for the installed version, and it destroys every row if the process dies after the drop — silently, because the retry then sees a fresh current-schema table and concludes there was nothing to migrate. The 953-line durable-snapshot + cross-process-lock + replay-merge subsystem that existed only to survive that drop has been deleted; do not rebuild it. Nothing is dropped now, so there is nothing for a crash to destroy
- All four tables use the one path, `emails` included. `emails` rows are re-fetchable from Gmail, but each carries an embedding that costs a paid API call to rebuild and `""` is already the documented legacy account sentinel, so in-place is both cheaper and leaves zero drop-and-recreate migrations in the tree
- Migrations need no lock, but they DO need to tolerate a table another process is still committing. `initDb()`'s `initPromise` is module-local and does not serialize a `serve` against a CLI run — and does not need to: `addColumns` and `createEmptyTable` are single MVCC commits, the loser of a race fails loudly ("Column already exists" / "Table already exists"), and `ensureTableColumns` re-probes the table's current schema before accepting the winner's commit rather than assuming a failure means somebody else did it. Observed over five forked two-process runs: one commit lands, one fails, zero rows lost in every interleaving. There is no longer a drop window for a concurrent queue write to fall into
- **`tableNames()` and `openTable()` disagree while a table is being created.** `tableNames()` enumerates the on-disk `*.lance` directories, so a name is LISTED before its `_versions/1.manifest` is committed, and `openTable()` rejects it in that window with `Table 'X' was not found` — byte-identical to the error for a table that never existed. That was a real startup crash, not a test artifact: whichever of a `cron` fetch and `serve` lost the race on a new or newly-migrated database died with a message naming nothing actionable. `openCommitted()` in `db/migrations.ts` wraps every `openTable` on the migration path and retries ONLY while the name is still listed — the listing is the only evidence that separates "another process is mid-create" from "this table is not there", because the message does not. Bounded at 1/2/5/10/25/50/100/200ms; a name that is absent, or an error that is not "not found", is rethrown on the first attempt. Verified 2026-08-07 against the installed binary: window 0.31–0.47ms, closing on the SECOND `openTable` in 6 of 6 observations, `mkdir X.lance` reproduces the state with no timing at all, two concurrent `createEmptyTable` calls never both succeed (40 of 40), and only `openTable` is affected — `schema()`/`countRows()` on a held handle never failed in 120 trials. Do NOT make the retry unbounded (an abandoned half-created directory must report, not hang) and do NOT add a lock
- The `pending_operations` migration is covered end-to-end in `db/schema-migration.test.ts`: real temp-directory LanceDB, tables seeded in the OLD shape, rows in `applied`/`rejected`/`failed`/`applying`/`pending`, both halves of a concurrent-init race, and a refusal that leaves the rows intact. The create race is driven DETERMINISTICALLY rather than by `Promise.all` and luck — `mkdir <db>/<table>.lance` reproduces the listed-but-uncommitted state exactly, and a `Connection` wrapper commits the winner's table between the loser's first and second `openTable`, so attempt 1 always fails against real uncommitted state and attempt 2 always succeeds. Keep it that way: the timing-dependent version of these tests passed 12 of 12 runs while the bug was live, and all four tables go through the one `ensureTableColumns` path, which is why the failing table name used to vary run to run
- The only delete path on `pending_operations` is `prunePendingOperations()`; `PRUNABLE_STATUSES` is `applied`/`rejected` only. `failed` is kept deliberately (it is the diagnostic record of an attempted mutation), `pending`/`applying` are unresolved
- `PendingOperationRecord.claimedAt` and `AppConfig.retention` are REQUIRED. Both were optional for one wave only, so that a branch which could not edit the other packages did not invalidate their fixtures. An optional declaration on a field that is always present invites a fallback for an `undefined` the system cannot produce — and for `retention` the fallback a reader reaches for is `0`, which means "keep every record forever"
- `emails` table has `accountId` column — must be included in all insert records
- **Every unbounded scan must pass `limit(UNLIMITED_QUERY_ROWS)`** (`db/utils.ts`). **LanceDB applies a DEFAULT LIMIT OF 10 to a plain FILTERED query, not just to vector searches.** Measured on a real 25-row table against `@lancedb/lancedb` 0.15.0 (2026-08-07): `countRows()` answered 25, `query().toArray()` and `query().where("status = 'pending'").toArray()` both answered TEN. `limit(0)` is NOT "no limit" — it is zero rows. Before the fix the approval queue listed at most 10 queued Gmail changes however many were queued (and `approvals apply` / the web Apply acted on those ten), `claimPendingOperations`' read-back-by-token was capped at 10 so an apply could mutate Gmail for rows it never learned it owned, `getStaleApplyingOperations` could omit stranded rows, `getEmails` returned 10 whatever `limit`/`offset` was asked for, and the batched email lookup rendered every email past the tenth as "not in local DB". The old `email-lookup.ts` carried a comment asserting the opposite as fact and it had never been checked. Pinned by `db/query-limit.test.ts`
- **`mergeInsert` does not work on these tables. Do not reach for it.** Two independent reasons, both measured against 0.15.0 (2026-08-07): (1) `createEmptyTable(name, schema)` builds NON-NULLABLE columns — apache-arrow's `Field` defaults `nullable = false` — while LanceDB infers `nullable = true` from the plain JS objects handed to `execute()`, and `mergeInsert` refuses the mismatch (`` `id` should have nullable=false but nullable=true ``, once per column) where `table.add()` coerces; (2) the join key is composed as `target_<key>` and parsed as an UNQUOTED SQL identifier, so a camelCase key like `accountId` folds to `target_accountid` and fails with `No field named target_accountid`, with no escape — backticking yields `` target_`accountId` `` and fails differently. `email-agent fetch` therefore could not store a single email on any fresh install until 2026-08-07. `upsertEmails` is delete-then-append over a predicate GROUPED BY ACCOUNT; `accountId IN (a,b) AND id IN (p,q)` is a cross product that deletes pairs the batch never named
- **Cross-process claim atomicity is CONFIRMED, not assumed** (`db/cross-process-claim.race.test.ts`): two forked node processes over one directory, three contested rows, six barrier-synchronised rounds — exactly one owner every round, zero rows claimed twice, and the winner alternates. It is deterministic because a handle is pinned to its open version, not because of timing. **The loser of a raw `table.update()` gets an ERROR (`Commit conflict for version N`), not a silent no-op**, so any write that is supposed to lose a race quietly MUST go through `updateAtLatestVersion` — which refreshes and retries, turning the conflict into the zero-rows-won the claim protocol assumes. An AST case in that test fails if a `table.update()` is added to `db/pending-operations.ts` outside the wrapper. `db/emails.ts` and `db/clusters.ts` deliberately take the raw error; they are single-write non-queue paths where a failed request the user can repeat is the right outcome
- All `.where()` string interpolation must use `escapeSql()` from `db/utils.ts` — LanceDB has no parameterized queries
- LanceDB's DataFusion SQL parser folds unquoted identifiers to lowercase — wrap camelCase columns in backticks (e.g. `` `actionId` = '...' ``) or queries fail with `No field named actionid`. See `emails.ts` for the convention
- **A LanceDB `Table` handle is PINNED to the version it was opened at.** Verified against `@lancedb/lancedb` 0.15.0 on a real temp-directory table (2026-08-07) by racing two handles over one row: a handle advances only through its OWN writes; `query()` on a handle another writer has moved past returns the OLD rows with no error; `update()` on such a handle THROWS `Commit conflict for version N` rather than committing or matching nothing; `checkoutLatest()` refreshes it in place. Any multi-step read/write sequence over one handle must therefore refresh before each step, or a sequence meant to degrade into "my predicate now matches nothing" explodes instead, and a read-back taken to count what a write reached can be a snapshot from before someone else's commit. `table.delete()` behaves exactly like `update()` here — it THROWS the same commit conflict — and `countRows()` behaves like `query()`, answering from the stale snapshot with no error (measured: 6 where the table held 5). `db/pending-operations.ts` routes every MULTI-STEP sequence through `updateAtLatestVersion`/`deleteAtLatestVersion`/`queryAtLatestVersion` (refresh + bounded conflict retry): `claimPendingOperations`, `resolveClaimedOperations`, `resolveStrandedApplyingOperations` and `prunePendingOperations`. The rest are single-step — one fresh handle, one operation, nothing after it to go stale — and the module header names each one, so "which of these is safe?" is answered rather than assumed. The prune case was not theoretical: it counts then deletes, its only caller swallows failures by design, so the un-refreshed version made the retention sweep quietly stop running whenever anything else was writing.
- **Never chain `.where()`** — LanceDB's `where()` maps to `onlyIf`, which REPLACES the previous predicate instead of ANDing it, so `query().where(A).where(B)` silently matches B only (verified against `@lancedb/lancedb` 0.15.0). Always join with `" AND "` into one string. `buildEmailFilters()` / `buildPendingOperationFilters()` return arrays for exactly this join; `countEmails` passes the same combined string to `table.countRows(filter)`

### Config
- `loadSettings()` re-reads the file on every call and keys its cache on a sha256 of the bytes read. Do NOT restore an unconditional cache, and do NOT key it on `mtime + size`: that is not file identity (`git checkout`, a restore from backup and `rsync --times` all reproduce a timestamp, and two settings differing only in a boolean are the same length), and `gmail.autoApplyActions` is the kill switch for unattended Gmail mutation — a stale copy keeps auto-applying after the user turns it off
- `loadSettings()` fails CLOSED on a settings file it cannot use. ENOENT alone means "absent, first run, defaults are right"; every other errno and an unparsable file THROW. Absence of information must never read as permission to destroy data: the defaults set `retention.approvalQueueDays` to 365 while the explicit opt-out is 0, and the post-approval sweep in `actions/approval.ts` reads it, so a momentarily unreadable file used to delete audit rows the user had explicitly opted out of pruning
- Next.js does **not** guarantee one module instance per process. Verified from a production build: every route entry requires the single shared `webpack-runtime.js` (one module registry), but webpack does not always place a module in a shared chunk — `app/api/auth/callback/route.js` carries its own inlined copy of `config/defaults.ts` + `config/settings.ts` (distinctive literals appear in `chunks/982.js`, `chunks/170.js` **and** that route entry). So a process-global invalidation hook like `clearSettingsCache()` only clears the caller's own copy; the per-call re-read is what makes every instance converge, and it is load-bearing rather than belt-and-braces
- A new top-level settings section survives a web settings PUT (`mergeSettingsUpdate` spreads `...current` first), but it is invisible to the settings UI until `sanitizeSettingsForResponse` lists it. A new key inside `gmail.*` does NOT survive: `normalizeGmailConfig()` rebuilds that section from the two auto-apply booleans alone
- The consent invariant has ONE implementation: `normalizeAutoApplyConsent()` (`config/settings.ts`, exported from `@email-agent/core/config`), which `normalizeSettings` calls. Enforcing it a second time at the web API boundary is deliberate defense in depth, and `normalizeGmailConfig()` in `packages/web/src/modules/api/validation.ts` is now a CALL to it rather than a hand-written duplicate. Keep the second enforcement point; never re-add a second implementation
- Dotted-path config writes belong in `config/dotted-path.ts` (`setNestedConfigValue`/`getNestedConfigValue`), which refuse `__proto__`/`constructor`/`prototype` in any position, including the terminal one. That is hygiene, NOT a fix for a live hole: the pollution route was probed and fails today only because `normalizeSettings` always writes both consent flags as own properties, which shadow the polluted prototype. `packages/cli/src/commands/config.ts` now calls them; it kept private copies that refused nothing until 2026-08-07, so the guard finally has a caller
- A removed settings key whose loss changes behaviour must announce itself. `gmail.syncActions` and `oauth` (a dead Google client-secret field, never read for authentication — see below) each warn ONCE per `(path, kind)` per process from `loadSettingsFromPath`, keyed on `legacyNoticeKey(path, kind)` rather than on the bare path: two independent legacy keys can be present in the same file on the same cache miss, and a bare-path key would let whichever check runs first mark the path warned and silently suppress the other's notice. `loadSettings()` re-reads the file on every call, so a notice hung off the read prints once per request — detection sits on the parse (cache-miss only) AND behind the warned-set, because an edit that leaves a legacy key in place is a genuine cache miss
- The `gmail` section's type is `GmailAutoApplyConfig` (was `GmailSyncConfig`, named for a `syncActions` field that no longer exists — the old name pointed readers at the unrelated `gmail/sync.ts` pipeline)

- **NOT COVERED and must not be described as covered:** React component rendering (there is no component testing library in this repo), Next itself (routing, middleware, streaming, server components), a SUCCESSFUL Gmail mutation (no linked account — every apply path in the tests ends in a per-operation failure), and the action runner's agent half
- **Every CLI prompt goes through `packages/cli/src/prompt.ts`.** Three rules live there, all of them shipped bugs first:
  1. **Never `rl.question()`.** `readline/promises` settles a pending question only on a `line` event and pauses input between questions, so at EOF — piped input, a redirect, or Ctrl-D mid-review — the promise never settles, commander's action promise hangs, and node exits **0** with every decision already collected silently discarded. `approvals review`, `run-action`'s `[a/r/S]` prompt and `actions snapshots restore`'s confirmation all did exactly that. `withPrompt`/`askOnce` drain the interface's async iterator instead, so buffered lines are delivered and `null` means real EOF.
  2. **Ctrl-C ABORTS; EOF does not.** Node's readline closes the interface on `^C` when nothing is listening for `SIGINT` (`if (this.listenerCount('SIGINT') > 0) this.emit('SIGINT'); else this.close()`), and a closed interface ends the iterator — byte-identical to EOF. Without the listener, `^C` half-way through `approvals review` classified as `stop` and the y answers were APPLIED TO GMAIL. The two must differ: EOF keeps what was decided (piped input running out is the normal end of a scripted review), SIGINT discards everything and exits **130**. Aborting costs a re-run and loses nothing; committing on Ctrl-C costs a mutation no surface here can undo. Only TERMINAL mode emits `SIGINT` — with piped stdin `^C` kills the process before any commit, which is the same outcome by a different mechanism.
  3. **One session per command, threaded through every prompt** (`usingPrompt`). Two sequential interfaces over one stdin LOSE INPUT: the first is in flowing mode and has already buffered the piped lines when it closes, so the second sees immediate EOF. `printf 'r\ny\nn\n' | email-agent run-action junk` silently discarded both review answers for exactly that reason, and porting off `rl.question()` did not fix it.
  `classifyReviewAnswer`/`classifyStrandedAnswer`/`confirmedYes` are pure, so the DEFAULT — anything unrecognised keeps the change queued — is under test. `prompt.test.ts` drives node's own `^C` decoding over a `terminal: true` PassThrough pair (there is no pty here, so a real terminal is not observed) and carries an AST tripwire that fails if `.question()` or a second `createInterface` appears anywhere in the CLI

- **Local-only enforcement is the bind, not the headers.** `mutationGuardResponse`/`readGuardResponse` (`packages/web/src/modules/api/validation.ts`) check the `Host` header **read straight off the request**, `Origin` and `Sec-Fetch-Site` — all of which a non-browser caller sets itself. **Never derive the host from `request.url`:** installed Next composes that URL from the server's own configured hostname (`attachRequestMeta` in `next/dist/server/next-server.js`; the render server defaults the hostname to `localhost`), so under both `next dev --hostname 127.0.0.1` and `next start --hostname 127.0.0.1` every request reaches the handler claiming `http://localhost:<port>` whatever `Host` arrived. The earlier version did exactly that, and it broke both ways: the browser that opened the `http://127.0.0.1:3847` URL Next itself prints got 403 on every mutation, and a DNS-rebound `Host: evil.example` was never seen at all, so the anti-rebinding property did not exist. `Origin` now has to name a local hostname on the port the caller addressed, so `localhost` and `127.0.0.1` both work while another app on `localhost:8080` does not; `X-Forwarded-Host` is deliberately ignored, since a rebound page is same-origin with itself and can set it. They buy anti-DNS-rebinding and anti-CSRF for *browsers*, plus a speed bump: mutations now require at least one of `Origin`/`Sec-Fetch-Site` to be present, so a bare `curl -X POST -H 'Host: localhost:3847'` is refused. The actual boundary is that `next dev`/`next start`/`email-agent serve` bind `127.0.0.1`, so an off-box process cannot open the socket at all. **Every** handler under `packages/web/src/app/api` carries a guard: mutations `mutationGuardResponse`, reads `readGuardResponse` (`/api/approvals`, `/api/approvals/count`, `/api/gmail`, `/api/gmail/[id]`, `/api/gmail/unread-count`, `/api/accounts`, `/api/actions`, `/api/actions/[id]/results`, `/api/actions/user`, `/api/settings`). For an exemption that names a weaker guard the route should still call, the test additionally scans the handler body for that guard's name, so a written reason can never mask a route running with no guard at all. Reads deliberately do NOT require the fetch metadata (Origin/Sec-Fetch-Site) — that part of "the address bar and local debugging still work" is unchanged. What DID change on 2026-08-22: both guards now also require a session cookie (`sessionViolation`, folded in after the header checks — see the unlock bullet above), so a bare `curl` read with no cookie now gets 401, not mail. The address bar still works because the browser carries the cookie automatically; the documented way to keep bare `curl`/scripted local debugging working is the same escape hatch named two sentences down. `EMAIL_AGENT_ALLOW_REMOTE_MUTATIONS=1` relaxes every header check (it short-circuits `localRequestViolation` outright) and, via `email-agent serve`, also opens the bind to `0.0.0.0`. Rows in `action_results` written BEFORE 2026-08-07 carry the old per-executor measurements and are **not comparable** with newer ones — `createdAt` is the only discriminator — and `Int32` is a real ceiling for anything summing the column, since one codex request costs ~21k tokens
- **Codex bills ~21k tokens for a one-word reply** — real, not a bug: it ships its own system prompt, tool definitions and skill descriptions on every request. Don't "fix" it by discarding the number
- **CLI stdout parsing goes in an exported pure function** (`parseClaudeCliOutput`, `parseCodexOutput`, `parseGeminiOutput`) so it can be unit-tested without spawning anything — some of these CLIs can't run in CI at all (gemini requires interactive browser OAuth)
- **`isAvailable()` must answer "can this run a prompt?", not "is the binary installed?"** `GeminiExecutor.isAvailable()` probed `--version` alone, so with the CLI installed and never signed in it returned true; the router selected gemini and the CLI blocked on an interactive browser consent screen until the 120s `execFile` timeout — one dead run per attempt, reported as a timeout. It now also requires credential material (`geminiCredentialSource`: `GOOGLE_API_KEY`/`GEMINI_API_KEY`, `~/.gemini/oauth_creds.json`, `GOOGLE_APPLICATION_CREDENTIALS`, the Vertex pair, the keychain opt-in — all read out of the installed `@google/gemini-cli` 0.54.4, not from docs), and `execute()` spawns with `NO_BROWSER=1` so an unauthenticated run fails in ~4s with a message naming the fix instead of hanging. Neither proves the credentials WORK; only a real call can, and a successful gemini run is still unverified
- **Gemini `--output-format json` has no `stats.totalTokenCount`** — the real path is `stats.models[<model>].tokens.total` (snake_case; `stats` is the raw `uiTelemetryService.getMetrics()` object). A failed run comes back as an `error` object with **no** `response` field, so treat that as an error rather than empty text
- **The API executors take an injectable `baseURL`/`apiKey`/`model`** (defaults unchanged). That seam exists so `api-executors.test.ts` can drive them against a local `node:http` stub — don't remove it; it is the only coverage those paths have without spending money
- Core module changes (via tsconfig `paths`) may not hot-reload in Next.js — restart `npm run dev` after modifying `packages/core/` source
